# 云同步冲突专项手测

## 文档导航

- 快速执行：`docs/manual-test/cloud-sync-checklist.md`

- 推荐执行顺序：`docs/manual-test/cloud-sync-recommended-order.md`

本文档专门覆盖多端编辑冲突、删除冲突、媒体记录冲突，以及冲突后的状态收敛与可见性。

---

## 测试目标

- 验证同时编辑同一条记录时，两端最终是否收敛
- 验证冲突时用户修改是否被静默吞掉
- 验证是否会生成冲突副本，以及副本是否可识别
- 验证删除与编辑同时发生时，行为是否稳定
- 验证带媒体记录在冲突后是否仍可用

---

## 通用前置条件

- [ ] 设备 A、设备 B 登录同一账号
- [ ] 云同步已开启
- [ ] 两端网络正常
- [ ] 可访问同步状态页
- [ ] 建议先准备 3 条专用测试记录：
- [ ] `CONFLICT-TEXT-BASE-001`
- [ ] `CONFLICT-DELETE-BASE-001`
- [ ] `CONFLICT-PHOTO-BASE-001`

---

## 场景 1：双端同时编辑同一条文本

**目标**
验证最典型的文本内容冲突。

**步骤**

- [ ] 确认 A/B 都能看到 `CONFLICT-TEXT-BASE-001`
- [ ] A 打开详情页，但先不要刷新 B
- [ ] B 也打开详情页
- [ ] A 编辑内容为 `CONFLICT-A-TEXT`
- [ ] A 保存
- [ ] B 在未刷新前编辑同一条内容为 `CONFLICT-B-TEXT`
- [ ] B 保存
- [ ] 等待 A 同步稳定
- [ ] 等待 B 同步稳定
- [ ] 查看 A 的最终主记录内容
- [ ] 查看 B 的最终主记录内容
- [ ] 查看列表中是否出现冲突副本
- [ ] 查看同步状态页中是否出现冲突相关提示或计数变化

**预期结果**

- [ ] A/B 最终主记录内容一致
- [ ] 不应长期一边一个版本
- [ ] 用户修改不应无声消失
- [ ] 如果实现了冲突副本，应能看到副本并识别来源

**重点观察**

- [ ] 主记录最终是 A 版本还是 B 版本
- [ ] 另一版本有没有作为冲突副本保留
- [ ] 是否出现重复 2 条以上记录

---

## 场景 2：A 编辑后，B 基于旧页面再次编辑

**目标**
验证“陈旧页面提交”是否属于稳定冲突路径。

**步骤**

- [ ] 确认 `CONFLICT-TEXT-BASE-001` 已同步到 A/B
- [ ] B 先打开详情页停留不动
- [ ] A 编辑内容为 `STALE-A-UPDATE`
- [ ] A 保存并等待几秒
- [ ] B 不刷新页面，直接把旧页面中的记录改为 `STALE-B-UPDATE`
- [ ] B 保存
- [ ] 等待两端同步完成
- [ ] 检查 A/B 最终内容和副本情况

**预期结果**

- [ ] 行为稳定可重复
- [ ] 不出现两端长期不一致
- [ ] 不出现记录消失

---

## 场景 3：A 删除，B 同时编辑

**目标**
验证删除与编辑同时发生时的冲突表现。

**步骤**

- [ ] 确认 A/B 都有 `CONFLICT-DELETE-BASE-001`
- [ ] A 删除该记录
- [ ] B 在未刷新前打开这条记录详情
- [ ] B 修改内容为 `DELETE-VS-EDIT-B`
- [ ] B 保存
- [ ] 等待两端同步完成
- [ ] 查看 A 首页结果
- [ ] 查看 B 首页结果
- [ ] 查看是否出现冲突副本或异常残留

**预期结果**

- [ ] 最终行为稳定且一致
- [ ] 不出现“删了又回来又删掉”的反复抖动
- [ ] 不出现首页已经删除但详情还能打开的残留状态

**重点观察**

- [ ] 最终是删除胜出还是编辑胜出
- [ ] 是否有冲突副本保存 B 的修改

---

## 场景 4：A 编辑，B 删除

**目标**
验证与场景 3 相反方向的冲突是否一致。

**步骤**

- [ ] 恢复一条新的共同记录，命名 `CONFLICT-DELETE-BASE-002`
- [ ] A 编辑为 `EDIT-VS-DELETE-A`
- [ ] B 在未刷新前删除这条记录
- [ ] 等待同步完成
- [ ] 查看两端最终结果

**预期结果**

- [ ] 行为与场景 3 至少保持一致性，不应随机
- [ ] 不应产生多条重复或僵尸记录

---

## 场景 5：双端同时编辑带照片的记录

**目标**
验证照片记录的文本元数据冲突不会破坏媒体可用性。

**步骤**

- [ ] 确认 A/B 都有 `CONFLICT-PHOTO-BASE-001`
- [ ] A 修改说明文字为 `PHOTO-CONFLICT-A`
- [ ] B 在未刷新前修改说明文字为 `PHOTO-CONFLICT-B`
- [ ] 等待同步完成
- [ ] 查看两端主记录最终说明文字
- [ ] 查看列表是否出现冲突副本
- [ ] 打开图片详情，检查缩略图和原图

**预期结果**

- [ ] 主记录最终收敛
- [ ] 图片本身仍可显示
- [ ] 不应因文字冲突导致图片丢失

---

## 场景 6：A 删除照片记录，B 同时编辑文字

**目标**
验证带媒体记录在删除冲突场景下是否稳定。

**步骤**

- [ ] 准备一条双方都有的照片记录 `CONFLICT-PHOTO-DELETE-001`
- [ ] A 删除该照片记录
- [ ] B 在未刷新前编辑其说明文字为 `PHOTO-DELETE-CONFLICT-B`
- [ ] 等待同步完成
- [ ] 查看两端最终列表和详情页表现

**预期结果**

- [ ] 不出现空白照片卡片残留
- [ ] 不出现已删除记录还能打开详情但图片失效的半残状态

---

## 场景 7：冲突后再次编辑，验证是否可恢复正常同步

**目标**
验证冲突处理后的记录仍能继续参与正常同步，不会永久损坏。

**步骤**

- [ ] 承接前面任一冲突场景，找到冲突后的主记录
- [ ] 在 A 再次编辑主记录为 `POST-CONFLICT-AFTER-EDIT`
- [ ] 保存并等待同步
- [ ] B 刷新查看

**预期结果**

- [ ] 主记录后续还能正常同步
- [ ] 不会一直卡在冲突状态
- [ ] 不会再次无故生成更多副本

---

## 场景 8：检查冲突在状态页与列表中的可见性

**目标**
验证冲突是否对用户可见，而不是静默发生。

**步骤**

- [ ] 在制造冲突后打开同步状态页
- [ ] 查看是否有 conflict copies、冲突数量或异常提示
- [ ] 返回首页，观察是否能从列表中识别出冲突副本
- [ ] 打开副本查看内容是否对应本地修改版本

**预期结果**

- [ ] 冲突有可见痕迹
- [ ] 副本内容与用户修改一致
- [ ] 用户能区分主记录与冲突副本
