## 背景

当前仓库已经具备账号、同步、云端概览、设置页同步区块等实现骨架，但产品表达仍容易混淆以下 3 件事：

- 用户是否已经登录
- 当前设备是否已经开启云同步
- 当前本地数据是否已经受到云端保护

如果继续把这些概念混在一个“cloud mode / 联网版”里，会带来 4 个直接问题：

- 用户会把“登录账号”误解为“切换到另一套产品”
- 用户会把“关闭同步”误解为“退出本地版 / 切回本地版”
- 代码层会把身份状态、同步状态和数据归属混成一个布尔开关
- 设置页和状态提示难以稳定表达“本地优先”这一核心承诺

本设计不重写底层同步协议。底层增量同步、冲突处理和本地优先同步内核继续以既有文档为准：

- [2026-03-22-backend-incremental-sync-protocol-design.md](/Users/cooper/Documents/code/MemoryCapsule/docs/superpowers/specs/2026-03-22-backend-incremental-sync-protocol-design.md)

本设计只定义上层产品形态、状态边界、切换语义和设置页信息架构。

## 目标

- 明确 DayCapsule 只有一个主产品，不再并列维护“本地版”和“联网版”两套产品心智
- 明确联网能力只作为当前本地数据的同步、备份和恢复增强层
- 明确登录、开启同步、关闭同步、退出账号这 4 个动作的语义边界
- 为现有 `authStore`、`syncStore`、设置页和状态提示提供稳定的一致表达

## 非目标

- 不设计第二个独立 App 或长期双包发布策略
- 不在本次范围内扩展分享、协作、网页访问或 AI 能力
- 不重写后端协议、媒体上传或冲突算法
- 不引入新的数据主权模型，例如“云端为主”或“本地 / 云端双空间并存”

## 最终方案

### 1. 产品定位

DayCapsule 定义为：

`一个本地优先的记忆记录 App。`

它在未登录状态下就是完整可用的产品。登录不会把用户切换到另一套产品，只会让当前本地数据具备云同步、云备份和恢复能力。

因此对外不再强调：

- 本地版
- 联网版
- 云端版

统一改为强调：

- 本地优先
- 已登录 / 未登录
- 云同步已开启 / 未开启
- 当前数据已受云端保护 / 尚未受保护

### 2. 核心心智

用户始终只操作同一个内容空间，也就是当前设备上的本地工作区。

这个工作区有且只有两层附加能力：

- 身份层：我是谁，是否拥有账号
- 保护层：这份本地数据是否已经和云端建立同步、备份、恢复关系

产品不引入第二个内容宇宙，不引入“切到云空间后看另一套数据”的常规路径。

### 3. 状态模型

产品状态拆成 3 层，禁止继续用单个“cloud mode”概念同时表示全部状态。

#### 3.1 身份状态 `auth state`

只回答用户是否已建立身份：

- `signed-out`
- `signed-in`

身份状态不表示：

- 是否已经开启同步
- 当前数据是否已经上传
- 当前工作区是否已受保护

#### 3.2 保护状态 `protection state`

只回答当前本地工作区是否已和云端建立保护关系：

- `unprotected`
- `activation-pending`
- `protected`
- `sync-error`

建议产品文案围绕“保护”组织，而不是围绕“模式切换”组织。

#### 3.3 工作区归属 `workspace attachment`

只回答当前本地工作区是否绑定到账号：

- `local-only`
- `attached-to-account`
- `detached`

这里的关键约束是：工作区本体始终在本地，账号绑定关系只是附着关系，不是主数据源切换。

### 4. 动作语义

4 个关键动作必须有稳定边界。

#### 4.1 登录

登录只建立身份，不自动上传、不自动覆盖、不自动迁移。

登录成功后的默认语义是：

- 你已有账号
- 当前数据仍只在本机
- 你可以选择是否开启云同步与备份

#### 4.2 开启云同步

只有在用户显式确认后，才允许把当前本地数据初始化到云端并建立持续同步关系。

如果云端为空，这一步的语义是：

- 为当前本地数据建立云端初始备份

如果本地和云端同时存在数据，则继续沿用既有本地优先同步设计中的初始化分支与一次性决策流程，不在本设计中改写。

#### 4.3 关闭云同步

关闭同步的语义是：

- 停止该设备继续与云端交换变更

关闭同步不是：

- 退出账号
- 删除本地数据
- 切回另一套本地版产品

#### 4.4 退出账号

退出账号的语义是：

- 解除身份会话

默认行为应是保留本机数据，不自动删除本地内容。任何清理本地数据的动作都必须作为单独、显式且危险的操作存在。

### 5. 首次启用云保护流程

首次启用流程收敛为 3 步。

#### 第一步：未登录状态

设置页表达为：

- 当前数据保存在本机
- 登录后可开启云备份与多设备同步

按钮文案建议优先使用：

- `登录以开启云备份与同步`

避免使用会暗示产品分层或功能残缺的文案，例如：

- 登录使用完整版
- 切换到云端版

#### 第二步：登录成功

登录成功后不立即同步，先进入确认页或确认弹窗，明确告知：

- 当前数据仍以本机为主
- 开启后会把当前本地内容备份到云端
- 后续可用于恢复与多设备同步

建议动作：

- `开启云同步`
- `暂不启用，仅保持登录`

#### 第三步：显式开启同步

用户点击 `开启云同步` 后，再执行首次同步初始化逻辑。

如果本地有数据、云端为空，此时体验文案应定义为：

- 正在为当前记忆建立云备份

而不是：

- 正在切换到云端模式

### 6. 信息架构

设置页中应把 `本地数据`、`云同步与备份`、`账号` 三件事拆开，而不是塞进同一个“云端模式”区块。

#### 6.1 本地数据

该分组始终存在，且优先级高于账号。

展示内容建议包括：

- 当前数据保存在本机
- 本地记录数
- 媒体占用空间
- 导出、本地备份、修复等设备内操作

这个区块负责强化“我拥有什么”。

#### 6.2 云同步与备份

该分组负责表达“这份数据是否被保护”。

按状态展示：

- 未登录
  - 文案：`未开启云备份与多设备同步`
  - 动作：`登录账号`
- 已登录未开启同步
  - 文案：`账号已登录，当前数据仍仅保存在本机`
  - 动作：`开启云同步`
- 已开启同步
  - 文案：`该设备正在同步，云端已保护当前记忆`
  - 信息：上次同步时间、失败项、待同步项
  - 动作：`立即同步`、`暂停此设备同步`

这个区块负责回答“是否已受保护”。

#### 6.3 账号

账号单独成组，但排在“云同步与备份”之后，只放身份相关操作：

- 当前账号信息
- 更换账号
- 退出登录
- 账号删除入口

这个区块负责回答“我是谁”。

#### 6.4 危险操作

单独放在最底部，避免和常规切换动作混在一起。

可包含：

- 清除本机数据
- 解除该设备同步关系
- 清空云端备份（如果未来支持）

### 7. UI 表达原则

主界面和设置页中的所有表达应满足以下原则：

- 不把“登录”说成切换产品
- 不把“同步”说成切换空间
- 不把“关闭同步”说成回到本地版
- 不把“本地优先”说成阉割版或试用版

首页状态提示应轻量，不打断记录流程。

建议首页只展示：

- 已同步
- 待同步
- 同步失败

不建议在首页持续展示以下标签：

- 本地版
- 联网版
- 云端模式

### 8. 与现有实现的对齐约束

现有代码中已经存在账号、同步状态、设置页同步入口和云端概览能力。后续实现收口时应遵守以下约束：

- 继续坚持本地 SQLite 是 UI 唯一主数据源
- 不再把“是否登录”与“是否开启同步”混成单个布尔状态
- 文案层面尽量淡化 `cloud mode`，强化“本地优先 + 云保护层”
- 设置页组件边界按“本地数据 / 云同步与备份 / 账号”收拢
- 任何 destructive 行为都不得作为常规模式切换的副作用

### 9. 为什么不选其他方案

#### 不选双空间

本地空间和云空间分离虽然边界干净，但会显著提高切换、迁移、冲突和用户认知成本，不适合当前产品阶段。

#### 不选双发行形态

两个包或两套长期并行发行形态会让发布、测试、配置、文案和支持成本翻倍。当前仓库已有完整 app + backend 结构，但还不值得用发行形态去表达产品层分叉。

#### 不选云端为主

这会直接削弱“本地版就是本地版”的独立性，也会让离线可用性和数据主权表述变弱，不符合当前产品定位。

## 测试与验证建议

本设计对应的实现收口完成后，至少应验证以下事实：

- 未登录时，记录、浏览、编辑、删除都完整可用
- 登录后不发生自动上传
- 开启同步前，设置页明确显示“当前数据仍仅保存在本机”
- 开启同步后，状态提示围绕“已受保护”而不是“已切换模式”
- 关闭同步不会退出账号、不会删除本地数据
- 退出账号默认不会删除本地数据

## 后续实施建议

后续如果要进入实施阶段，建议按以下顺序拆任务：

1. 收拢术语与文案，减少“cloud mode / 联网版”表达
2. 收拢状态模型，拆开登录状态与同步保护状态
3. 调整设置页信息架构与入口文案
4. 补齐登录后未开启同步的显式确认流
5. 用现有前端测试覆盖新的状态与文案边界
