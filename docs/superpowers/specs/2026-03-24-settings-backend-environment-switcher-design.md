# Settings Backend Environment Switcher Design

## 背景

当前前端假设只有一个固定后端：

- API client 使用单一 base URL
- 登录态持久化在单一 MMKV 命名空间
- SQLite 数据库固定为单文件
- 媒体文件与缓存目录不区分后端环境

这会导致一个问题：如果用户切换到另一个后端域名，本地登录态、同步状态、数据库和媒体缓存都会与原后端混在一起，无法保证数据边界。

用户希望在前端设置中加入后端域名配置，并满足以下约束：

- 后端地址是全局配置，影响整个 App 的请求
- 设置页提供“测试连接”按钮
- 测试按钮只请求 `/health`，只判断服务可达
- 只有测试成功后，才允许保存并切换到新后端
- 设置项需要记忆最近使用过的域名，并以下拉形式供用户选择
- 切换到新后端后，自动清空当前登录态，要求重新登录
- 本地缓存数据需要按后端环境隔离，避免不同后端串数据

## 目标

实现一个“后端环境切换”能力，而不是单纯的字符串设置项：

1. 设置页支持输入、选择、测试、保存后端域名
2. App 全局请求基址可在运行时切换
3. 最近使用域名有记忆与下拉选择能力
4. 本地登录态、设置、同步状态、SQLite 和媒体缓存按后端环境隔离
5. 切换后端后自动退出登录，并进入新环境的本地数据空间

## 非目标

本次不覆盖以下范围：

- 鉴权有效性检测；测试按钮不校验 token，仅检测 `/health`
- Gitea / 部署链路改动
- 同一后端下多账号快速切换
- 自动数据迁移或多环境数据合并
- 后端 `/health` 协议变更

## 用户场景

### 场景 1：首次连接自托管后端

用户在设置页输入新的后端域名，点击“测试连接”。只有连接成功后，才允许点击“保存并切换”。保存后，App 进入新的后端环境，并要求重新登录。

### 场景 2：在多个测试/生产后端间切换

用户可以在下拉框中直接选取最近使用过的域名，再重新测试连接。测试通过后保存切换，进入对应环境的独立本地空间。

### 场景 3：切换后端后避免本地数据串环境

切换到另一个后端时，旧环境的登录态、同步状态、SQLite 数据库和媒体缓存不再被当前环境读取。新环境若尚未初始化，则创建新的空环境。

## 方案选择

### 方案 A：只新增后端域名设置，不隔离本地数据

优点：

- 改动最少

缺点：

- 不同后端环境会共享登录态、同步状态、数据库与媒体缓存
- 极易产生数据串环境与错误同步

不采用。

### 方案 B：按后端域名隔离环境

每个后端域名对应一个独立环境，拥有自己的：

- API base URL
- 登录态
- 设置
- 同步状态
- SQLite 数据库
- 媒体目录

优点：

- 数据边界清晰
- 能满足“最近域名切换 + 测试成功后保存 + 切换后重新登录”的完整闭环

这是本次采用的方案。

### 方案 C：按后端域名 + 用户双层隔离

优点：

- 边界最严格

缺点：

- 第一版复杂度偏高
- 当前需求中切换后端已强制重新登录，不需要先做到用户二级隔离

暂不采用。

## 交互设计

在设置页新增一个“后端连接”卡片，建议放在“账户”区域下方或相邻位置。卡片包含：

1. 一个可输入、可展开历史记录的域名下拉输入框
2. 一个“测试连接”按钮
3. 一个连接状态区域
4. 一个“保存并切换”按钮

### 输入框与历史记录

- 页面打开时，输入框展示当前已保存的后端域名
- 用户可以手动输入新域名
- 用户也可以从最近使用域名列表中选择历史地址
- 最近使用列表建议保留最近 5 个，按最近成功保存排序并去重

### 测试连接按钮

- 请求目标：`<input-base-url>/health`
- 测试只校验服务是否可达，不校验登录态
- 状态包括：
  - 未测试
  - 测试中
  - 连接成功
  - 连接失败（带简短原因）

### 保存并切换按钮

- 默认禁用
- 只有“最近一次针对当前输入值的测试成功”后才启用
- 用户一旦修改输入框内容，之前的测试成功状态立即失效
- 用户选择历史域名后，也必须重新测试

### 保存成功后的行为

当用户点击“保存并切换”且新域名与当前域名不同：

1. 保存当前域名配置
2. 更新最近使用域名列表
3. 切换当前环境
4. 清空当前登录态
5. 重置依赖旧环境的数据状态
6. 打开新环境的数据空间
7. 提示“后端已切换，请重新登录”

如果新域名与当前环境相同，则不做真实切换，但仍允许刷新最近使用记录。

## 状态与数据模型

需要引入一个“后端环境”概念。

### EnvironmentConfig

- `currentServerUrl`: 当前生效域名
- `recentServerUrls`: 最近使用域名列表

### BackendConnectionDraft

这是设置页内的草稿状态，不建议直接持久化：

- `draftUrl`
- `testStatus`
- `testedUrl`
- `testErrorMessage`

### Environment Key

不能直接把原始 URL 当文件名。需要先做规范化，再转换为安全 key，例如：

- 统一移除末尾 `/`
- 保留 scheme、host、port
- 转为安全字符串或 hash

示例：

- `http://localhost:3000`
- `https://api.example.com`

可进一步映射为：

- `env_http_localhost_3000`
- `env_https_api_example_com`

或直接使用哈希作为内部 key。

## 本地存储结构

### MMKV

当前 `Storage` 只有一个固定的 `app-storage`。本次需要引入“环境作用域”的 key 规则，而不是继续把所有状态写在固定 key 上。

建议结构：

- 全局 key
  - `backend:currentServerUrl`
  - `backend:recentServerUrls`
- 环境 key
  - `env:<serverKey>:auth:token`
  - `env:<serverKey>:auth:refreshToken`
  - `env:<serverKey>:auth:user`
  - `env:<serverKey>:settings:*`
  - `env:<serverKey>:sync:*`

这意味着现有 `settingsStore`、`authStore`、`syncStore` 的 key 读取逻辑都要改成带环境前缀。

### SQLite

当前 SQLite 数据库文件是固定的单文件。需要改为按环境生成数据库文件名，例如：

- `MemoryCapsule-<serverKey>.db`

切换环境后，数据库实例需要重新绑定到对应数据库文件。

### 文件目录

媒体目录也需要隔离，建议结构：

```text
media/
  environments/
    <serverKey>/
      photos/
      voice/
      cache/
```

这样不同后端的媒体文件不会共享目录。

## 模块边界

### 1. BackendEnvironmentStore / Service

职责：

- 读取当前环境
- 保存当前环境
- 管理最近使用域名
- 提供规范化 URL 与生成 `serverKey` 的能力

### 2. BackendConnectionService

职责：

- 只负责测试连接
- 请求 `<baseUrl>/health`
- 返回结构化结果，不直接操作 UI

### 3. ApiClient Base URL Resolver

职责：

- 全局请求时从当前环境读取 base URL
- 环境切换后，新请求自动走新地址

这要求 `getApiClient()` 不再依赖固定的初始化值，而是能感知当前环境变化，或在环境切换后被显式重置。

### 4. LocalEnvironmentDataManager

职责：

- 切换本地环境
- 计算数据库文件名和媒体目录
- 重置旧环境相关运行时状态
- 清空当前登录态
- 打开新环境的数据空间

## 切换流程

推荐的保存并切换顺序：

1. 用户输入域名
2. 点击“测试连接”
3. 请求 `<draftUrl>/health`
4. 测试成功，解锁“保存并切换”
5. 用户点击保存
6. 规范化 URL，生成 `serverKey`
7. 持久化当前环境和最近使用列表
8. 切换数据库和媒体目录到新环境
9. 清空当前登录态
10. 重置依赖旧环境的数据 store
11. 提示重新登录

要求整个切换流程具备原子性思路：

- 不能出现“环境已切到新地址，但数据库仍是旧环境”的半切换状态
- 如果切换初始化失败，应保留旧环境不变

## 错误处理

### 输入校验失败

- 输入为空
- 不是合法的 HTTP/HTTPS URL
- 不允许保存，也不允许发起测试

### 测试连接失败

- DNS 失败
- 网络失败
- 请求超时
- 返回非 2xx

统一反馈为“连接失败，请检查地址或网络”，必要时附带简短原因。

### 切换失败

如果保存时发生异常：

- 不更新当前环境
- 不清空旧登录态
- 不重置旧数据空间
- 给出明确错误反馈

## 测试策略

### 单元测试

- URL 规范化
- `serverKey` 生成
- 最近使用域名去重、排序、裁剪
- 测试成功门禁逻辑

### 组件测试

- 设置页展示当前域名
- 输入后点击“测试连接”会请求 `/health`
- 修改输入后，旧测试成功状态失效
- 只有测试成功后才可保存
- 选择历史域名后仍需重新测试

### 环境切换测试

- 保存切换后会清空登录态
- 切换后使用新的环境 key
- 切换后打开新的数据库文件/媒体目录
- 不同域名的本地状态互不污染

## 兼容性与迁移

现有用户已经有单实例本地数据。第一版需要给出明确迁移策略：

- 默认将当前固定数据库与固定存储 key 视为“当前默认后端环境”
- 首次引入环境隔离时，把现有单实例状态映射到当前生效的默认服务器
- 若用户从未配置过后端域名，可继续使用现有默认 URL 作为初始环境

第一版不要求把历史数据自动拆分到多个环境；只需确保新架构启用后，后续切换不会再串环境。

## 风险

### 1. 环境切换影响范围大

这不只是设置 UI 改动，还会影响认证、同步、数据库和媒体路径。必须避免分散实现。

### 2. SQLite 切库时机

现有 SQLite 是单例打开方式。要评估并改造数据库实例管理，确保环境切换后能重新指向新文件。

### 3. 媒体路径兼容

现有媒体 URI 解析依赖固定目录结构。引入环境目录后，需要保证旧 URI 仍有可控兼容策略。

## 验收标准

满足以下条件即认为完成：

- 设置页新增后端域名下拉输入与最近历史记录
- 测试连接按钮使用 `/health`
- 只有测试成功后才允许保存
- 保存后全局 API 请求走新域名
- 切换后自动清空登录态
- 登录态、设置、同步状态、SQLite 与媒体目录按后端域名隔离
- 不同后端环境的本地数据互不污染
