## 背景

当前三类卡片的创建体验并不一致：

- 文本卡片基本是即时写入，本身体验接近“立刻出现”。
- 照片卡片要等压缩、缩略图、持久化等本地文件处理结束后才 `addLocalEntry`，用户在首页会明显感到等待。
- 语音卡片虽然已经有“停录后再异步处理”的优化，但停止后的本地保存、路径写入、上传前准备仍和最终可展示状态耦合，无法统一成“所有卡片都先出现，再补全”。

这导致首页列表的产品语义不统一：

- 有些卡片代表“我已经创建了这条内容”
- 有些卡片代表“系统把所有重处理做完后，才算创建”

用户已经明确希望优先看到卡片内容本身，哪怕媒体后处理稍后完成。因此本轮需要把三类卡片统一成“先插卡、后补全”的模型，同时保持失败时不留下半成品垃圾数据。

## 目标

- 文本、照片、语音三类卡片统一为“先出卡片，再异步补全”
- 列表中的新卡片应尽量展示已有内容，而不是只显示笼统 loading
- 补全过程成功时更新同一条 entry，而不是创建第二条记录
- 补全过程失败时删除该 entry，并清理本次产生的本地文件
- 该模型同时适用于离线模式与在线/云端模式
- 不把本轮扩大成新的任务系统、队列系统或全局基础设施重构

## 最终方案

### 1. 总体策略

统一采用“已入库占位卡片 + 异步本地补全”：

1. 创建入口先生成稳定 `entryId`
2. 用最小可展示内容把 entry 写入本地数据库
3. `entry.localReadyState = 'processing'`
4. 后台执行该类型对应的本地补全逻辑
5. 成功后更新同一条 entry，切到 `localReadyState = 'ready'`
6. 失败后删除同一条 entry，并清理本次创建过程中写入的本地文件，再弹错误提示

本轮不引入独立 job 表，也不引入第二套“仅在前端内存存在”的临时卡片模型。

### 2. 状态模型

#### 2.1 新增 `localReadyState`

在 entry 顶层新增本地准备状态，独立于现有 `syncStatus`：

- `processing`
  - 卡片已创建并可出现在首页
  - 但本地媒体或内容准备还未完成
- `ready`
  - 卡片内容已具备正常展示所需的本地数据

这个状态只描述“本地展示准备是否完成”，不表达同步语义，也不进入后端同步协议。

#### 2.2 保持 `syncStatus` 的既有职责

`syncStatus` 继续只处理同步与上传语义：

- `pending`
- `pending_upload`
- `uploading`
- `synced`
- `failed`
- `pending_delete`
- `conflict-local-copy`

本轮不复用 `syncStatus` 表达“本地处理中”，避免把“本地媒体准备”与“云同步状态”混成同一个状态机。

#### 2.3 失败语义

本轮不引入“processing_failed”之类的长期失败状态。

原因：

- 用户已确认失败时直接删卡
- 若失败卡片长期保留，会与现有 `failed` 同步语义冲突
- 会把当前问题升级成“本地任务恢复产品设计”，超出本轮范围

## 各类卡片行为

### 1. 文本卡片

- 文本卡片创建时直接写入最终内容
- 默认 `localReadyState = 'ready'`
- 不需要额外占位 UI
- 文本入口仍保留当前接近即时完成的行为

文本卡片纳入本轮的意义主要是统一状态模型，而不是重做其创建链路。

### 2. 照片卡片

#### 2.1 最小可展示内容

照片卡片创建时立即写入：

- `type = 'photo'`
- 稳定 `entryId`
- 最小 `media[]`
- 优先使用选图器/相机返回的临时本地 URI 作为预览图
- `localReadyState = 'processing'`

卡片出现后：

- 主图优先显示已有本地预览
- 时间、类型、卡片框架立即可见
- 媒体角落或元信息区域显示轻量“准备中”提示

#### 2.2 本地补全内容

照片补全阶段负责：

- 压缩
- 缩略图生成
- 正式持久化路径写入
- 完整性元数据补齐
- 在在线/云端模式下，为后续上传队列准备正式本地媒体路径

补全成功后：

- 用正式本地路径替换临时预览路径
- 回写 `thumbnail`
- 回写尺寸、hash、完整性元数据
- 切到 `localReadyState = 'ready'`

### 3. 语音卡片

#### 3.1 最小可展示内容

语音卡片在“录音结束”后立即创建：

- `type = 'voice'`
- 稳定 `entryId`
- 已知时长
- 基础图标与文案
- `localReadyState = 'processing'`

卡片出现后：

- 先显示时长与基础元信息
- 播放区域展示不可点击占位
- 文案显示“准备中”而不是“上传中”

#### 3.2 本地补全内容

语音补全阶段负责：

- 录音文件本地保存
- 必要的播放资源准备
- 回写最终本地媒体路径
- 在在线/云端模式下衔接现有上传队列

补全成功后：

- 语音卡片切到可播放态
- `localReadyState = 'ready'`
- 后续再按现有规则进入 `pending_upload / uploading / synced`

本地准备完成之前，不允许把“不可播放”伪装成“已经完成”。

## 数据流

### 1. 文本创建流

1. 用户提交文本内容
2. 直接写入本地 entry
3. `localReadyState = 'ready'`
4. 在线/云端模式下按现有规则继续同步

### 2. 照片创建流

1. 用户拍照或选图
2. 立即生成 `entryId`
3. 使用最小 `media` 与临时本地预览 URI 写入 entry
4. `localReadyState = 'processing'`
5. 首页立即出现照片卡片
6. 后台执行压缩、缩略图、正式落盘、元数据补齐
7. 成功后更新同一条 entry 为正式照片内容
8. `localReadyState = 'ready'`
9. 在线/云端模式下再继续进入现有上传链路

### 3. 语音创建流

1. 用户点击停止录音
2. 立即生成或确认稳定 `entryId`
3. 以时长等最小信息写入语音卡片
4. `localReadyState = 'processing'`
5. 首页立即出现语音卡片
6. 后台执行本地保存、媒体路径回写、播放可用性准备
7. 成功后更新同一条 entry
8. `localReadyState = 'ready'`
9. 在线/云端模式下再继续进入现有上传链路

## 模块边界

### 1. `HomeScreen / app/app/(tabs)/index.tsx`

职责：

- 响应文本、照片、语音的创建动作
- 先创建最小 entry
- 调用对应类型的补全 service

不再负责：

- 把照片或语音的完整本地处理细节全部堆在页面文件里

本轮建议顺手把“照片补全”“语音补全”拆成独立 service/controller，避免首页入口继续膨胀。

### 2. `entryStore` 与本地 DB

职责：

- 支持保存 `localReadyState`
- 支持创建最小 entry
- 支持原地更新同一条 entry 为完成态
- 支持按 `entryId` 删除处理中 entry

该层应保证“插卡、更新、回滚删除”都围绕同一条记录进行。

### 3. 照片补全服务

职责：

- 接收已创建的照片 entry
- 完成本地压缩、缩略图、正式媒体路径生成
- 回写正式 media 数据
- 返回补全过程中创建的文件列表，供失败回滚清理

不负责：

- 卡片 UI 渲染
- 云端同步结果判断

### 4. 语音补全服务

职责：

- 接收已创建的语音 entry
- 完成本地文件保存与播放可用性准备
- 回写最终 media 数据
- 返回补全过程中创建的文件列表，供失败回滚清理

不负责：

- 首页交互编排
- 上传队列执行本身

### 5. `EntryCard` 与子组件

职责：

- 根据 `localReadyState` 渲染“处理中半成品态”或“正式完成态”
- 不直接关心文件处理细节

显示规则：

- `processing`：稳定布局 + 局部占位
- `ready`：走现有正式内容展示

## 错误处理

### 1. 补全失败的统一规则

无论照片还是语音，只要本地补全过程失败：

1. 删除对应 `entryId` 的 entry
2. 删除本次补全过程中新建的本地文件
3. 从当前列表中移除该卡片
4. 弹出错误提示
5. 记录结构化日志

这里的删除顺序优先保证“用户不要继续看到半成品卡片”。

### 2. 删除失败时的兜底

如果理论上的“回滚删除”也失败：

- 当前页面内存列表至少不能继续保留这条 processing 卡片
- 记录错误日志
- 启动阶段的 processing 清扫会再次兜底

本轮不引入更复杂的“失败回滚失败恢复机制”。

### 3. 上传队列边界

上传队列不应接手 `localReadyState = 'processing'` 的媒体卡片。

只有本地准备完成、`localReadyState = 'ready'` 后，照片/语音才允许进入现有上传状态机。

## 应用重启策略

本轮对“残留 processing 卡片”采用启动清扫：

- 应用启动时扫描 `localReadyState = 'processing'` 的 entry
- 直接删除这些 entry
- 尝试清理其关联的本地临时文件
- 不做自动恢复续跑

原因：

- 与“失败直接删卡”的产品语义一致
- 实现复杂度明显低于任务恢复
- 避免用户在冷启动后继续看到无法确认是否还能完成的半成品卡片

## 影响范围

- `app/app/(tabs)/index.tsx`
- `app/src/store/entryStore.ts`
- `app/src/database/operations.ts`
- `app/src/database/migration.ts` 或对应 schema/migration 文件
- 照片保存与语音保存相关 service
- `EntryCard` 及其照片/语音子视图
- 首页列表相关测试

## 不在范围内

- 新建独立 job 表或本地任务中心
- 失败卡片保留与手动重试 UI
- processing 卡片跨重启自动恢复续跑
- 重做现有 `photoUploadQueue` / `voiceUploadQueue` 架构
- 后端协议改动
- 云同步状态枚举重设计

## 验收标准

- 文本、照片、语音创建后，首页都能立即看到对应卡片
- 照片卡片在本地补全期间优先展示已有预览，而不是空白框
- 语音卡片在本地补全期间显示时长和轻量占位，不伪装成可播放
- 补全成功时更新同一条 entry，不产生重复卡片
- 补全失败时卡片会从列表消失，并弹错误提示
- 在线/云端模式下，媒体卡片只有在本地准备完成后才进入现有上传链路
- 应用重启后不会长期残留 `processing` 卡片
