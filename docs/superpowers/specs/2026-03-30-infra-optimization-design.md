# 工程优化设计

## 背景

当前项目的主要工程问题不在功能缺失，而在维护基线和启动链路复杂度：

- `app/app/_layout.tsx` 同时承担应用初始化、迁移、鉴权恢复、同步恢复、前后台生命周期处理和自动备份，职责过重。
- `app/package.json` 中存在已声明但未实际落地的依赖，增加维护噪音。
- `README.md` 中部分描述与当前仓库真实状态不一致，容易误导后续开发。

本轮不处理用户正在推进的测试问题，也不主动改动会影响现有测试结论的行为逻辑。

## 目标

本轮优化仅包含三项：

1. 将根布局中的启动编排逻辑拆分到独立 bootstrap/service 层。
2. 清理确认未使用的依赖，优先处理 `@tanstack/react-query`。
3. 修正文档失真，让 README 反映当前真实工程状态。

## 非目标

- 不修复用户已在处理的样式 lint 问题。
- 不改动现有业务行为、同步策略或数据结构。
- 不引入新的状态管理框架或新的初始化机制。
- 不做大范围死代码清理。

## 方案对比

### 方案 A：只改文档和依赖

优点：风险最低，改动小。

缺点：无法触及当前最明显的维护痛点，`_layout.tsx` 仍然会继续膨胀。

### 方案 B：拆启动链路，同时收口依赖和文档

优点：能处理当前最高价值的结构问题，同时把低风险的依赖和文档问题一起收口。

缺点：需要谨慎保持初始化行为不变，避免引入启动回归。

### 方案 C：借机全面重构启动、同步和生命周期层

优点：理论上最彻底。

缺点：范围明显超出本轮需求，容易和正在进行的测试工作冲突。

推荐采用方案 B。

## 设计

### 1. 启动链路解耦

保留 `app/app/_layout.tsx` 作为根入口，但把当前散落在组件内的大段初始化逻辑抽离到单独模块。拆分后保持以下边界：

- `RootLayout` 只负责渲染根 Provider、注册必要的 React 生命周期和调用编排入口。
- `app bootstrap` 模块负责一次性启动任务编排。
- `app lifecycle` 模块负责前后台切换时的恢复、同步与备份逻辑。

启动任务继续按现有语义执行，但在结构上分成两类：

- 阻断启动任务：文件系统、音频、数据库初始化、数据库迁移。
- 启动后恢复任务：登录恢复、sync store 恢复、cloud mode 恢复、待上传语音/照片补偿、顶部同步状态刷新。

为了控制风险，本轮不改变任务顺序与失败处理策略，只把代码搬到清晰的函数边界中。

### 2. 生命周期逻辑收口

当前 `_layout.tsx` 内部还维护了 `AppState`、网络恢复与挂起恢复相关逻辑。本轮会把这些逻辑整理为可复用函数，但不改变现有触发条件：

- 后台时：仍按当前条件触发自动备份。
- 回到前台时：仍执行 cloud sync、语音补传、照片补传、顶部同步状态刷新。

目标是让组件只保留订阅与清理，具体流程放在 service 内，降低闭包复杂度和未来继续扩散的风险。

### 3. 依赖清理

先基于实际引用确认 `@tanstack/react-query` 未使用，再从 `package.json` 中移除，并同步更新 lockfile。

本轮只移除可确认未使用、且不会影响构建或运行的依赖，不做推测性删减。

### 4. 文档修正

README 只修正与本轮直接相关且已经确认失真的内容，包括：

- 不再宣称当前仓库处于“零 tsc 错误”或其他与现状不一致的健康状态。
- 对样式规范、工程状态和检查命令做更准确表述。
- 若某些检查当前已知受迁移中问题影响，文档明确说明，而不是继续写成已全部完成。

## 文件级改动预期

- 调整：`app/app/_layout.tsx`
- 新增：`app/src/services` 或相邻目录下的 bootstrap / lifecycle 编排模块
- 调整：`app/package.json`
- 调整：`app/pnpm-lock.yaml`
- 调整：`README.md`

具体命名以贴合现有目录结构为准，优先使用最少的新文件数。

## 风险与控制

### 风险 1：启动回归

控制方式：

- 只做结构性搬移，不改业务条件判断。
- 改后至少运行 `pnpm run typecheck`。
- 若 lint 仍停留在已知样式问题，不将其视为本轮新增失败。

### 风险 2：误删依赖

控制方式：

- 先全仓确认无直接引用。
- 移除后重新跑类型检查，确保构建入口未受影响。

### 风险 3：README 再次失真

控制方式：

- 只写已经验证过的现状。
- 避免写绝对化表述，尤其是“全部通过”“零错误”之类结论。

## 验证

本轮完成后至少执行：

- `pnpm run typecheck`
- `pnpm run lint`

对 `lint` 的判断标准是：不引入新的 lint 失败；若仍保留当前已知样式迁移问题，应在结果中明确说明。

## 实施原则

- 最小正确改动，避免顺手重构。
- 不碰用户正在处理的测试/样式问题。
- 先保证结构更清晰，再考虑后续扩展空间。
