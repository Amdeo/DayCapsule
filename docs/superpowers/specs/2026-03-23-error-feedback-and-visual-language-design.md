## 背景

当前 app 已经有一些可延续的视觉线索，但还没有形成稳定、可复用的视觉语言：

- 时间线、搜索栏、详情页、编辑页大多使用暖白底和圆角卡片
- 内容类型已经形成 `文字紫 / 照片青 / 语音橙` 的识别色
- 但通用按钮、强调色、页面底色、弹层风格仍然比较分散
- 一部分组件更偏“纸感记录产品”，另一部分又更像“蓝白工具页”

同时，错误反馈目前主要依赖分散的原生 `Alert.alert(...)`：

- [app/app/_layout.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/app/_layout.tsx)
- [app/src/components/LoginPage.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/src/components/LoginPage.tsx)
- [app/src/components/SettingsPage.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/src/components/SettingsPage.tsx)
- [app/src/components/BackupPage.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/src/components/BackupPage.tsx)
- [app/app/(tabs)/index.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/app/(tabs)/index.tsx)

这带来三个直接问题：

- 视觉上，错误提示仍然是系统弹窗，和现有页面气质断开
- 工程上，错误提示散落在页面里，没有统一入口与分层
- 产品上，用户会感到 app 在正常浏览时是一个东西，报错时又突然变成另一套系统 UI

因此，本轮目标不是找一个“能弹框的包”立刻接入，而是先把视觉主线定下来，再基于这套主线设计并落地第一批统一错误反馈。

## 目标

- 明确整个 app 后续统一遵循的视觉语言基线
- 让错误反馈成为第一批落地的品牌化组件，而不是继续使用默认系统弹窗
- 保持 `文字 / 照片 / 语音` 三种类型色的强识别，但收束在统一暖纸感基底中
- 建立一套全局可复用的错误反馈边界与调用方式
- 本轮只实现“视觉规范 + 错误弹层 + 第一批关键错误场景接入”
- 不在本轮顺手重做全部旧页面

## 方案取舍

本轮已比较三种路线：

### 1. 自写品牌化错误反馈层

结论：采用。

理由：

- 最适合承接“先统一视觉语言，再落地组件”的目标
- 能直接按本次定下的纸感视觉做出专属弹层
- 未来新页面与新组件可以复用同一套设计 token 和反馈模式

代价：

- 需要自行定义宿主、API、去重策略与动效
- 但本轮范围较小，可控

### 2. 包做轻提示，自写错误弹层

结论：本轮不采用。

说明：

- 典型候选包括 `react-native-toast-message`、`react-native-flash-message`
- 这条路线适合未来补轻提示，但不适合本轮作为主轴

放弃原因：

- 会同时引入两套反馈语言
- 当前用户目标是“先定整套 app 风格”，而不是先补齐所有提示组件种类

### 3. 直接接入通用 Dialog UI 库

结论：本轮不采用。

说明：

- 典型候选包括 `react-native-paper` 的 `Dialog + Portal`

放弃原因：

- Material 气质和本轮确认的“温润纸感记忆册”方向不一致
- 容易把 app 从“记录产品”带回“系统工具”的视觉表达

## 最终方案

### 1. 视觉主线

整套 app 的统一主线定为：

`温润纸感记忆册`

具体约束如下：

#### 1.1 底色体系

- 页面主底色使用暖米白，而不是纯白
- 卡片、弹层使用比背景略亮或略厚的暖白层级
- 层次主要靠底色明度差与轻阴影，而不是靠高反差描边

设计意图：

- 保留“记忆产品”的温度
- 避免 app 退化成蓝白工具页

#### 1.2 层级材质

所有主要界面元素统一理解为“纸面上的卡片层级”：

- 页面底面：纸面
- 普通卡片：轻浮层
- 错误弹层：更高一级的厚卡片

不采用：

- 玻璃拟态
- 强科技感光泽
- 高饱和系统风弹窗

#### 1.3 类型色规则

保留现有三种高识别类型色：

- `文字`：紫
- `照片`：青
- `语音`：橙

使用位置：

- 类型徽标
- 时间线圆点
- 局部描边
- 局部浅色底
- 类型状态点缀

限制：

- 不把整页大面积涂成类型色
- 让类型色服务于识别，而不是主导整个页面

#### 1.4 通用强调色

除类型色外，新增一个统一的通用强调色，建议为偏陶土的暖红棕。

主要用于：

- 错误弹层主按钮
- 危险操作
- 需要用户立即处理的提示

设计意图：

- 让“错误态 / 需要处理”的视觉语义与“内容类型”彻底分开
- 避免把 `文字紫` 既当类型色又当错误主色

#### 1.5 形状语言

形状目标是“大圆角，但不幼态”。

建议统一节奏：

- 普通卡片：`18-20`
- 输入框与按钮：`12-16`
- 主错误弹层：`22-24`

要求：

- 不同页面和组件不能继续自由漂移圆角尺度
- 形状统一是后续页面风格稳定的关键约束之一

#### 1.6 文本气质

- 标题文本使用偏暖灰棕，而不是纯黑
- 正文文本比标题轻一级
- 辅助说明再浅一级

设计意图：

- 提升整体阅读感
- 避免冷白背景下的系统工具感

### 2. 错误弹层设计

本轮先设计并实现一套主错误弹层组件，但内部支持三种使用等级。

#### 2.1 错误等级

##### 阻断型错误

用于：

- 登录失败
- 同步失败
- 保存失败
- 初始化失败

表现：

- 居中弹层
- 遮罩背景
- 主按钮 + 次按钮

##### 决策型错误

用于：

- 权限被拒绝后引导去设置
- 同步冲突后选择处理路径
- 导入/恢复失败后决定下一步

表现：

- 沿用同一套弹层骨架
- 支持 `2-3` 个操作按钮

##### 弱错误

本轮不实现为新组件。

说明：

- 不值得强打断用户的弱提醒，后续可再扩展为 `toast/snackbar`
- 这次先不同时铺开第二套反馈体系，避免范围膨胀

#### 2.2 视觉结构

错误弹层的外观不再是系统 Alert，而是纸面上的厚卡片：

- 暖白底
- 大圆角
- 轻阴影
- 明确的内容分区

结构顺序：

- 顶部状态标记
- 中部标题
- 中部说明文案
- 可选的补充说明 / 建议
- 底部按钮区

#### 2.3 颜色规则

- 错误主色：陶土红棕
- 普通正文：暖灰棕
- 次级说明：更浅的暖灰
- 类型色 `紫 / 青 / 橙` 不直接承担错误主色角色

设计意图：

- 错误语义独立
- 保持整体气质克制
- 不让“类型识别色”与“错误反馈色”互相污染

#### 2.4 按钮规则

- 默认右侧主按钮，左侧次按钮
- 主按钮承担：
  - `重试`
  - `继续`
  - `去设置`
- 次按钮承担：
  - `取消`
  - `稍后`
  - `我知道了`

仅危险动作使用更深、更饱和的暖红棕填充。

#### 2.5 文案规则

- 标题一句话说结果
- 正文一句话说原因或下一步
- 不把原始技术异常直接完整展示给用户
- 具体异常细节保留给日志与监控，而不是主文案

#### 2.6 动效规则

- 遮罩淡入
- 弹层轻微上浮或缩放出现
- 不做夸张弹跳、抖动或强闪烁

设计意图：

- 有存在感
- 不突兀
- 不破坏整体“安静、温润”的产品气质

### 3. 组件边界与调用方式

#### 3.1 顶层全局宿主

在根布局中挂载一个全局错误反馈宿主，建议落在：

- [app/app/_layout.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/app/_layout.tsx)

宿主职责：

- 渲染统一错误弹层
- 处理显示队列或去重
- 保证任意页面和任意全局流程都能调用

#### 3.2 页面负责决定是否提示

页面或页面级流程改为调用统一入口，而不是直接写原生 `Alert.alert(...)`。

第一批典型调用方包括：

- [app/src/components/LoginPage.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/src/components/LoginPage.tsx)
- [app/src/components/SettingsPage.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/src/components/SettingsPage.tsx)
- [app/src/components/BackupPage.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/src/components/BackupPage.tsx)
- [app/app/(tabs)/index.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/app/(tabs)/index.tsx)
- [app/app/_layout.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/app/_layout.tsx)

调用目标建议统一为：

- `showFeedback(...)`
- 或语义更明确的 `showErrorFeedback(...)`

#### 3.3 service 层不直接弹 UI

底层 service 只负责：

- 抛错误
- 返回错误码 / 错误类型
- 记录日志

不负责：

- import 错误弹层组件
- 直接决定如何展示 UI

这样可以保证错误反馈始终由页面层或流程层决定，避免视觉入口继续散掉。

#### 3.4 三层错误体系并存

##### 第一层：业务错误弹层

负责本轮新体系：

- 登录失败
- 同步失败
- 保存失败
- 初始化失败
- 导入导出失败
- 权限失败并需要去设置

##### 第二层：原生确认框暂时保留

这类不是“错误提示”，而是“用户确认动作”，本轮不强行并入新组件：

- 删除确认
- 退出登录确认
- 重置设置确认

##### 第三层：致命崩溃继续交给 `ErrorBoundary`

- [app/src/components/ErrorBoundary.tsx](/Users/cooper/Documents/code/MemoryCapsule/app/src/components/ErrorBoundary.tsx)

它继续负责 crash 级别兜底，不与业务错误弹层混用。

#### 3.5 v1 API 约束

建议统一入口至少支持：

- 标题
- 说明文案
- 错误等级
- 按钮列表
- 可选场景 key

行为约束：

- 同类错误短时间内默认去重
- 一次只显示一个主错误弹层
- 避免连续多次弹出造成“炸屏”

### 4. 本轮实现范围

#### 4.1 需要实现

- 一份正式视觉规范与设计文档
- 一套全局错误反馈宿主
- 一套统一的错误反馈调用入口
- 一套符合本次风格的错误弹层 UI
- 第一批关键错误场景接入

#### 4.2 第一批接入场景

优先接入以下错误：

- 登录/注册失败
- 初始化失败
- 云同步失败
- 保存失败
- 导入/导出失败
- 权限失败且需要引导去设置

设计意图：

- 这些场景已经明显存在
- 现有 `Alert.alert(...)` 分布集中
- 替换收益最高

#### 4.3 明确不在本次范围

- 不重刷全 app 现有页面
- 不把所有确认框都改成自定义弹层
- 不引入 `toast/snackbar`
- 不改 crash 兜底逻辑
- 不顺手补全所有成功提示和普通通知

### 5. 验证与验收标准

#### 5.1 验收标准

实现完成时应满足：

- 存在统一的全局错误反馈宿主
- 存在统一的错误反馈调用入口
- 第一批关键错误场景不再直接散落调用原生 `Alert.alert`
- 错误弹层视觉符合本次确认的纸感风格
- 同类错误不会短时间重复连炸
- 原有确认框与致命兜底行为不被误伤

#### 5.2 验证方式

自动化验证：

- 组件测试：
  - 弹层渲染
  - 按钮行为
  - 去重策略
- 页面测试：
  - 登录失败
  - 同步失败
  - 权限失败
  是否走统一入口

手动验证：

- 不同页面触发错误时，视觉是否一致
- 文案是否遵守统一规则
- 遮罩、动效、返回行为是否正常
- 多次触发同类错误时是否存在重复轰炸

### 6. 风险与控制

本轮最大风险不是技术实现，而是范围蔓延。

必须坚持：

- 先统一错误反馈，不顺手重做页面
- 先做第一批关键错误，不试图一次清空全部 `Alert`
- 先建立标准，再逐步迁移其他提示类型

如果后续验证通过，这套错误弹层将成为新视觉语言在 app 内的第一块稳定基石，后续新页面与新组件都应优先复用同一套底色、层级、强调色与反馈模式，而不是重新发明自己的局部风格。
