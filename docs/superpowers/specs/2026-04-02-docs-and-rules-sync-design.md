# 文档与规则同步设计

## 背景

仓库代码已经经历多轮演进，近期提交集中在全文搜索、云同步、上传恢复、状态拆分与测试粒度调整等方向，但当前仓库中的主文档、测试说明和部分规则文档仍保留较早阶段的描述，已经与现状脱节。

这次工作的目标不是补未来规划，而是把“当前仍有入口价值、会被开发者或维护者实际打开的文档”更新为只陈述当前代码库中的既有事实。

## 目标

- 更新当前仍承担导航、使用说明、部署说明、测试说明和规则说明职责的文档。
- 清理明显失效的文件引用、命令、目录结构和架构描述。
- 让文档与当前仓库真实存在的文件、脚本、流程和能力保持一致。
- 保留历史设计文档的历史属性，不把历史 spec 伪装成当前实现说明。

## 非目标

- 不新增未来规划、路线图或待办事项。
- 不为尚未落地的能力补文档。
- 不对所有历史 spec 文档逐篇重写实现细节。
- 不覆盖用户当前工作区内已有但尚未提交的无关改动。

## 范围

### 重点更新文档

- `README.md`
- `docs/QUICK_REFERENCE.md`
- `docs/IMPLEMENTATION_SUMMARY.md`
- `docs/MANUAL_TEST_PLAN.md`
- `docs/BACKEND_DEPLOYMENT.md`
- `docs/manual-test/README.md`（若需要补充索引和关系说明）

### 规则文档处理原则

- 只处理已经确认与当前仓库事实冲突、且不会覆盖用户现有未提交改动的规则说明。
- 若规则文件在用户工作区已有未提交修改，则避免直接重写，优先更新其他入口文档。

### 历史文档处理原则

- `docs/superpowers/specs/` 下的设计文档默认保留为历史记录。
- 只有当某些历史文档被当前入口文档直接引用、且内容会误导读者理解当前实现时，才做最小必要修正或去引用处理。

## 已确认的失同步问题

### README

- 将应用描述为 `DayCapsule`，而仓库与包名已以 `MemoryCapsule` 为主。
- 混用了根目录与 `app/` 目录的安装与运行路径说明。
- 文档索引中包含当前仓库里并不存在或不再作为主入口的文档路径。
- 核心功能、测试能力和同步流程描述未完整反映当前实现。

### QUICK_REFERENCE

- 仍围绕较早版本的 `entryStore`、分页与标签规范化设计展开。
- 缺少当前测试脚本、云同步相关能力和现行目录结构的准确说明。
- 部分 API 和类型示例存在明显过期风险。

### IMPLEMENTATION_SUMMARY

- 仍以“三阶段存储重构”作为当前状态总结。
- 测试数量、阶段命名、架构重心与当前代码库明显不符。
- 需要改成面向当前代码库的“实现现状摘要”，而不是过时阶段总结。

### MANUAL_TEST_PLAN

- 仍以旧版存储重构验收为主线。
- 当前仓库已存在 `docs/manual-test/` 目录承载云同步相关测试用例，顶层手测文档应与之衔接，而不是重复陈述旧范围。

### BACKEND_DEPLOYMENT

- 文档仍引用 `nginx.conf`，而当前工作区该文件已删除。
- 需要根据真实存在的 `docker-compose.yml`、部署模板和当前后端结构校正部署说明。

## 设计方案

### 方案 1：入口文档全面校准，历史文档最小保留修正

做法：只更新当前仍被开发者实际使用的入口文档和必要规则文档；历史设计文档保留其历史属性，不承担“当前真相”职责。

优点：收益最大，修改面可控，不会破坏历史记录语义。

缺点：历史 spec 本身仍可能保留旧表述，但不会再被当作主入口。

### 方案 2：所有文档逐份改写成当前说明

做法：包括历史 spec 在内，尽可能把所有文档都改成描述当前实现。

优点：表面上一致性最高。

缺点：会模糊历史记录和当前说明的边界，维护成本高，也容易引入新的不一致。

### 方案 3：只改最外层 README 和少量主文档

做法：只修顶层 README 与少数入口页，其余保持不动。

优点：成本最低。

缺点：大量已知误导项仍会保留，不满足本次范围要求。

### 推荐方案

采用方案 1。

原因：它最符合“全部都看，但只写现状”的要求。这里的“全部都看”体现在完整排查所有高风险入口和引用关系，而不是把历史设计文档都改写成当前实现说明。

## 更新策略

### README

- 改为以当前仓库名和当前应用配置为准。
- 明确根目录与 `app/` 目录的职责边界。
- 校正开发命令、测试命令、文档索引和关键能力概览。
- 保留确有代码支撑的同步、搜索、媒体与测试说明。

### QUICK_REFERENCE

- 重新整理为“当前开发者快速入口”，优先保留稳定事实：目录结构、常用命令、主要测试脚本、关键服务/状态模块入口、当前手测文档入口。
- 移除或重写高风险的旧 API 摘录和阶段性架构图。

### IMPLEMENTATION_SUMMARY

- 从“阶段重构总结”改为“当前实现概览”。
- 以当前核心能力为主：本地数据、媒体处理、云同步、搜索、测试结构、部署结构。
- 只写仓库中已有实现，不写未来演进计划。

### MANUAL_TEST_PLAN

- 改成总览性质的手测入口文档。
- 说明顶层手测范围与 `docs/manual-test/` 下云同步专项用例之间的关系。
- 删除已经只对应旧重构阶段的验收措辞。

### BACKEND_DEPLOYMENT

- 以当前真实文件为准核对部署说明。
- 修正 Compose、环境变量、日志、上传目录与反向代理说明。
- 去除对失效文件或已不存在结构的引用。

## 数据来源与核对依据

文档改写只基于以下现状来源：

- `app/package.json`
- `app/app.json`
- `docker-compose.yml`
- 当前仓库实际目录与文件存在性
- 当前测试脚本与 `docs/manual-test/` 目录
- 近期提交记录反映的功能演进方向

## 验证策略

### 文档一致性验证

- 检查文档中引用的文件路径是否真实存在。
- 检查命令是否与当前脚本名称一致。
- 检查目录结构描述是否与当前仓库一致。

### 现状一致性验证

- 用 `app/package.json` 校对应用脚本、依赖和测试命令。
- 用 `app/app.json` 校对应用名称、slug 和平台配置。
- 用 `docker-compose.yml` 校对后端部署链路。
- 用 `docs/manual-test/` 校对手测入口说明。

## 风险与控制

- 风险：误把历史记录当作现状说明。
  控制：入口文档承担现状说明，历史 spec 保持历史属性。

- 风险：覆盖用户工作区已有未提交改动。
  控制：所有修改在独立 worktree 中进行，不直接操作当前工作区脏文件。

- 风险：文档写入了代码中尚未稳定的隐含行为。
  控制：仅记录当前仓库中可直接核对的事实，不补推测性结论。

## 预期产出

- 一组已校准的当前主文档与部署/测试说明。
- 更准确的项目入口信息，减少新旧文档混杂带来的误导。
- 对现有规则文档中明显失配部分的最小必要修正或绕开处理。
