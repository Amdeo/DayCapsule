# Home Timeline Interaction Regression Design

## 状态

- 当前状态：已确认设计，待写实现计划
- 用户确认日期：2026-03-27

## 背景

当前仓库已经为首页时间线补过一批 Jest 回归，包括：

- `timeline.controller.test.tsx`：覆盖时间线控制器的视图切换、滚动状态和编辑保存
- `timeline.home.navigation.test.tsx`：覆盖文本卡片进入详情页与编辑器的基础导航流
- `timeline.home.sync-status.test.tsx`：覆盖首页同步状态入口
- `renderHomeScreen.tsx`：提供首页级的轻量 harness，用于驱动 `entryStore`、设置态和同步指示态

现有覆盖已经能证明“局部组件能渲染”，但对首页时间线主交互仍有明显缺口：

1. 首页空态与列表态之间的切换没有被锁住
2. 列表分页触发与重复触发保护没有首页级回归
3. 首页时间线展示是否真实跟随 store 的筛选状态变化，仍缺少稳定回归
4. 从首页进入详情/编辑后，关闭动作是否能把页面状态收回，覆盖仍不完整

这些场景都属于“页面看起来还在，但交互状态已经悄悄错了”的典型回归点，优先级高于继续补纯渲染类断言。

## 目标

为首页时间线补一组高价值、低脆弱度的 Jest 页面级回归测试，并满足以下目标：

1. 锁住首页时间线空态与数据态的主展示切换
2. 锁住首页滚动分页对 `loadMore` 的触发契约
3. 锁住首页时间线对 store 搜索/筛选状态变化的展示联动
4. 锁住首页进入详情/编辑后的关闭与回落行为
5. 继续复用现有 `renderHomeScreen.tsx` harness，只做最小测试基础设施增强

## 非目标

本次不覆盖以下范围：

- Sidebar、FAB、同步状态、设置入口的额外回归
- 真正的 React Navigation 跨页面导航
- Android 返回键、前后台切换、系统弹窗
- 录音、拍照、上传队列等媒体链路
- 为测试目的重构首页业务逻辑

这些内容已经有单独测试或应放到其他计划中处理，不在本轮顺手扩展。

## 范围与分层

本次固定为 `Jest-Page` 范围，落点在首页壳层与时间线展示联动之间。

测试层级职责如下：

- `Timeline` 组件级测试：继续负责局部卡片交互和控制器行为
- 首页级 `renderHomeScreen` 回归：负责“首页装配后的时间线主交互”
- `Maestro`：不参与本轮，避免把页面级回归变成真机流程验证

换句话说，本轮要验证的是：

- 首页如何消费 `entryStore`
- 首页如何把 store 状态投射到时间线展示
- 首页交互结束后能否回到稳定的页面状态

而不是验证完整端到端导航闭环。

## 方案比较

### 方案 A：继续只补 `Timeline` 组件测试

优点：

- 改动最小
- mock 范围小

缺点：

- 无法覆盖首页壳层与时间线装配后的状态联动
- 仍然会漏掉“store 变了，但首页展示没跟着变”的问题

不采用。

### 方案 B：基于 `renderHomeScreen.tsx` 补首页时间线主交互回归

优点：

- 能覆盖首页真实使用到的 store/state 装配
- 复用现有 harness，新增成本低
- 稳定性比重型页面集成测试更好

缺点：

- 必要时要为 harness 暴露少量新的交互能力

这是本次采用的方案。

### 方案 C：直接补 `app/(tabs)/index.tsx` 的重型集成测试

优点：

- 更贴近真实页面

缺点：

- mock 面过大
- 测试更脆
- 很容易演化成“为了证明装配没坏而复制一套实现细节”

本轮不采用。

## 最终方案

### 1. 测试文件布局

本轮新增一个聚焦首页时间线主交互的测试文件，放在：

- `app/src/components/__tests__/timeline/`

命名遵循现有模式，表达“首页时间线交互回归”这一单一职责，不与现有 `navigation`、`sync-status` 测试混在一起。

### 2. Harness 策略

默认继续复用：

- `app/src/components/__tests__/helpers/renderHomeScreen.tsx`

约束如下：

1. 先用现有能力驱动测试
2. 只有当某个高价值用例无法表达时，才补最小 helper
3. 不为未来假设场景预先扩展大量 API
4. 不修改首页业务组件来迎合测试

如果要增强 harness，允许的改动类型只有：

- 暴露已有 store 状态更新能力
- 暴露列表滚动或分页触发的最小入口
- 暴露当前空态/列表态对应的稳定 testID

不允许的改动类型：

- 新增测试专用业务分支
- 改写首页数据流
- 引入和生产代码语义不一致的 mock 行为

### 3. 首批回归用例

本轮首批锁定 4 组行为。

#### `HT-01` 空态与数据态切换

- 前置条件：初始无记录
- 操作步骤：渲染首页，断言空态；随后把 harness/store 状态切成有记录
- 预期结果：空态消失，时间线列表出现
- 风险点：首页错误地缓存空态、未响应 store 更新

#### `HT-02` 分页加载触发契约

- 前置条件：时间线存在更多数据，`hasMore = true`
- 操作步骤：触发列表底部加载或等价的分页入口
- 预期结果：调用一次 `loadMore`
- 异常分支：当 `isLoadingMore = true` 时，不应重复触发

#### `HT-03` 首页筛选结果联动

- 前置条件：注入可被搜索词或标签过滤的数据集
- 操作步骤：通过现有 harness/store 更新搜索词或标签状态
- 预期结果：首页时间线展示结果同步变化
- 风险点：筛选逻辑只在 store 内变化，首页展示未重算或未刷新

#### `HT-04` 详情/编辑后的关闭回落

- 前置条件：存在至少一条文本记录
- 操作步骤：从首页进入详情或编辑，再执行关闭动作
- 预期结果：详情或编辑层关闭，首页回到稳定时间线视图
- 风险点：关闭后残留悬空弹层、视图未回落、局部状态未清空

### 4. 实现顺序

实现阶段按 TDD 执行，顺序固定为：

1. 先写 `HT-01`
2. 跑失败，确认失败原因正确
3. 做最小 harness 或测试修正
4. 跑绿
5. 再进入 `HT-02`
6. 重复到 `HT-04`

这样可以避免一开始就把 harness 扩成一大块基础设施。

### 5. 错误处理与边界

本轮测试设计明确约束以下边界：

- 如果某个行为只能靠大量 mock 首页内部私有实现才能验证，说明它不适合放在本轮首页级测试，应退回组件级或后续流程级测试
- 如果分页入口在当前 harness 中不可稳定表达，只允许补最小稳定触发点，不允许为了测分页而重写整个时间线 mock
- 如果关闭详情/编辑的行为已经在 `Timeline` 组件测试中完整锁住，则首页级只补“回到稳定页面状态”的那一层，不重复断言内部实现细节

## 验证方案

实现阶段的验证顺序固定为：

1. 每新增一条用例，先单独运行目标测试文件，确认失败再修
2. 首页时间线新文件全绿后，回归 `timeline` 相关现有 Jest 套件
3. 最后运行前端全量 Jest

本轮完成时，至少需要有以下验证证据：

- 新增首页时间线交互回归文件通过
- 相关 `timeline` 旧测试文件保持通过
- `cd app && pnpm test --runInBand` 通过

## 风险与取舍

本轮的核心取舍是：

- 优先补“首页状态联动回归”，而不是再补更多局部渲染断言
- 优先保持 harness 轻量可维护，而不是把它演化成首页的第二套实现

这意味着本轮不会追求“首页所有行为都测到”，而是优先补最容易静默回归、且最适合放在 `Jest-Page` 层的 4 条主交互链路。

## 后续扩展

如果本轮补完后 harness 仍然清晰，下一批可继续沿同一路径扩展：

1. 首页刷新状态与失败保留旧数据
2. 首页滚动过程中的 FAB/回顶按钮行为
3. 首页时间线与搜索浮层之间的打开/关闭联动
4. 首页和同步状态入口的组合回归

这些都不在本轮实现范围内，只作为后续扩展方向保留。
