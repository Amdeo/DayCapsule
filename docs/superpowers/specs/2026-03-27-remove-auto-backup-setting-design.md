# 自动备份设置移除设计

## 背景

当前设置页在“数据”分组展示“自动备份”开关，文案为“进入后台时自动保存到本地”。但应用本身采用本地优先存储，记录和媒体在创建时就已写入本地。该开关实际控制的是“应用进入后台时，按节流策略自动生成本地 ZIP 备份”，不是“是否保存到本地”。

这造成两个问题：

1. 文案误导用户，容易理解为关闭后数据不会保存在本机。
2. 自动生成恢复备份属于安全兜底能力，继续暴露为可关闭设置的价值较低。

## 目标

移除设置页中的“自动备份”开关，将后台自动本地备份收敛为默认开启策略，同时保留备份页中的手动导出/导入能力。

## 非目标

- 不改动 ZIP 备份格式、备份目录、保留数量和 24 小时节流策略。
- 不新增新的备份入口或新的备份提示文案。
- 不处理历史 `settings:autoBackup` 存储键迁移，只停止读取和写入。

## 方案

### 1. 后台自动备份改为无开关常驻策略

应用进入后台时，仅检查 `BackupService.shouldBackup()`；满足条件则创建本地 ZIP 备份。不再读取 `settings:autoBackup`。

### 2. 设置页移除自动备份项

删除设置页中对应的展示、props、控制器回调和 store 绑定，避免用户再看到该误导性开关。

### 3. 清理设置存储接口

从 `settingsStore` 中移除：

- `autoBackup` 状态
- `setAutoBackup`
- `settings:autoBackup` 键的读取、写入、重置逻辑

保留其余设置行为不变。

## 影响范围

- 设置页 UI 会少一个开关项。
- 后台自动备份从“用户可关”改为“始终启用但仍按 24 小时节流”。
- 依赖旧 testID 或旧 store 字段的测试需要同步调整。

## 风险与处理

### 风险 1：测试仍依赖旧开关

处理：更新设置页偏好测试、运行时回归测试和相关测试辅助，改为断言开关不存在、后台仅检查 `shouldBackup()`。

### 风险 2：历史数据用户担心行为变化

处理：不改变手动备份页入口；行为只从“可选后台备份”收敛为“默认安全兜底”。

## 验证

1. 设置页不再渲染 `settings-switch-auto-backup`。
2. App 进入后台时不再读取 `settings:autoBackup`。
3. `BackupService.shouldBackup()` 为真时仍会触发自动备份。
4. 相关 Jest 测试通过。
