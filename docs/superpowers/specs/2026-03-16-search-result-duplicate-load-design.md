# 搜索结果重复加载修复 — 设计文档

**日期：** 2026-03-16
**状态：** 已确认

## 背景

当前时间线的数据加载由 Zustand store 统一管理，搜索与筛选通过 `applySearchFilters()` 和 `applyFilters()` 刷新首屏结果，分页通过 `loadMore()` 追加后续数据。

现象表现为：

- 在搜索或筛选后返回首页，时间线有时会出现每条结果显示两次
- 退出应用再重新进入后，重复现象消失
- 清空筛选条件后，重复结果不会立刻恢复正常

这说明问题出在内存态列表或异步加载竞态，而不是 SQLite 中真的写入了重复记录。

## 根本原因

当前实现有两个结构性缺口，组合后会导致偶发重复：

1. `loadMore()` 直接执行 `entries + page` 追加，没有按 `entry.id` 去重
2. store 没有“查询会话”概念，旧请求即使已经过期，返回后仍然可以写回当前列表

因此，只要发生以下任一情况，就可能把同一批结果再次拼进内存：

- 搜索结果显示后，`SectionList` 的 `onEndReached` 在布局变化或列表回到首页时再次触发
- 旧查询的分页请求慢于新查询返回，晚到的结果覆盖或污染当前列表
- 同一页结果被重复请求并重复 append

由于这些问题只污染内存态 `entries` / `filteredEntries`，应用重启后重新从数据库首屏加载，重复现象自然消失。

## 目标

- 消除搜索与筛选结果中的偶发双份显示
- 让分页追加对重复请求保持幂等
- 让过期查询结果无法污染当前列表状态
- 保持现有 UI 与数据库接口不变，将修复收敛在 store 层

## 方案选择

### 方案 1：Store 会话隔离 + 结果去重（推荐）

在 `entryStore` 内维护当前查询签名或会话 id。所有首屏加载和分页加载都记录其所属会话，只有仍属于当前会话的请求才允许写回状态。分页追加时按 `entry.id` 去重。

优点：

- 直接解决竞态污染与重复 append 两类问题
- 修复集中在 store，UI 组件无需承担补救逻辑
- 能覆盖搜索场景之外的其他偶发重复加载

缺点：

- store 状态机会比现在复杂一些

### 方案 2：仅在 UI 层压制 `onEndReached`

在搜索返回首页后临时禁用一次 `onEndReached`，或在首帧稳定前不允许分页。

优点：

- 改动小

缺点：

- 只能缓解某一条触发路径
- 旧请求晚返回导致的污染仍然存在

### 方案 3：拆分普通列表与搜索列表状态

为默认时间线和搜索结果分别维护独立的 `items`、`cursor`、`hasMore`。

优点：

- 语义清晰，状态边界更强

缺点：

- 改动面明显更大
- 当前问题不需要通过大规模状态拆分来解决

**结论：** 采用方案 1，在 store 内实现查询会话隔离与分页幂等追加。

## 架构设计

### 查询签名

在 store 内新增一个“当前查询签名”，由以下字段稳定拼接而成：

- `searchQuery`
- `filterType`
- `filterDateRange`
- `selectedTags`

签名生成需要显式规范化，并使用稳定 JSON 序列化后的对象作为签名来源，而不是直接拼接裸字符串。推荐结构如下：

```ts
{
  query: searchQuery,
  type: filterType,
  dateRange: filterDateRange,
  tags: [...selectedTags].sort((a, b) => a.localeCompare(b)),
}
```

序列化时保持固定字段顺序，避免不同字段组合产生签名碰撞。

具体规范如下：

- `searchQuery` 使用当前字符串值
- `filterType` 使用当前枚举值
- `filterDateRange` 使用当前枚举值本身（`all` / `today` / `week` / `month`），不直接使用计算后的时间戳边界
- `selectedTags` 按标签名字符串做稳定升序排序后再参与签名生成

这样可以避免同一组筛选条件因为标签顺序、时间边界计算时机或序列化方式不同而被误判为不同查询。
该签名不是为了展示给 UI，而是为了标识“当前列表属于哪一组过滤条件”。

### 首屏加载

首屏加载应收口为统一流程。`loadEntries()`、`applyFilters()` 与 `applySearchFilters()` 的职责如下：

- `loadEntries()`：用于默认列表首屏加载，直接开启一轮新查询
- `applyFilters()`：用于基于当前 store 过滤状态开启一轮新查询
- `applySearchFilters()`：只负责批量写入 `searchQuery`、`filterType`、`filterDateRange`、`selectedTags`，随后委托给 `applyFilters()`，不单独维护另一套会话逻辑

也就是说，真正的“开启一轮新查询”行为只存在于共享首屏加载流程中，避免搜索入口与普通筛选入口出现不同步的状态机。

共享流程包含以下步骤：

1. 基于当前过滤条件生成新的查询签名
2. 写入 store 作为当前活动查询
3. 在同一次状态更新中重置 `cursor`、`hasMore`，并显式将 `isLoadingMore` 置回 `false`
4. 发起首页查询
5. 请求返回后，仅当该签名仍是当前活动查询时才允许在同一次状态更新中写回 `entries`、`filteredEntries`、`cursor`、`hasMore`、`isLoading`

如果请求返回时签名已经过期，说明用户已经切换了查询条件，这批结果直接丢弃。

### 分页加载

`loadMore()` 在发请求时捕获两项上下文：

- 当前查询签名
- 当前分页游标 `cursor`

同一查询下的并发分页策略保持保守：

- 如果 `isLoadingMore` 已为 `true`，新的 `loadMore()` 直接返回
- 不允许同一活动查询同时存在两次有效分页请求
- 因此，`cursor`、`hasMore`、`isLoadingMore` 始终只由当前这一次被接受的分页结果更新

请求返回后，只有在“签名未变化”的前提下才允许合并结果。合并逻辑不再直接做数组拼接，而是统一走 `mergeUniqueById(prev, page)`：

- 保留原有顺序
- 如果新页中存在已经加载过的 `entry.id`，只保留一份

只有当这次分页结果被接受时，才更新：

- `entries`
- `filteredEntries`
- `cursor`
- `hasMore`
- `isLoadingMore`

如果该请求已过期，则不更新任何分页状态。

### 去重策略

去重只放在 store 的 merge 阶段，不放到渲染层做：

- 首屏加载使用整页替换，不需要额外去重
- 分页加载使用按 `entry.id` 去重的稳定合并

这能保证去重成本仅发生在真实的数据合并点，不会变成每次渲染的持续开销。

## 错误处理

错误处理遵循“只有当前会话可以改状态”的原则：

- `loadEntries()` / `applyFilters()` 失败时，仅当请求仍属于当前活动查询，才将 `isLoading` 置回 `false`
- `loadMore()` 失败时，仅当请求仍属于当前活动查询，才将 `isLoadingMore` 置回 `false`
- 被判定为过期的请求不视为异常，不弹提示，仅记录开发日志
- 原有的数据库表未就绪重试逻辑保留，重试次数与终止条件保持现有实现不变
- 对于数据库表未就绪的自动重试，重试必须沿用最初那次首屏请求对应的查询签名快照；若该签名在重试触发前已过期，则这次重试直接放弃，不允许旧重试覆盖新查询
- 过期重试被放弃时，不主动改写 `isLoading`；因为一旦旧签名已过期，loading 状态的归属已经移交给新的活动查询，由新的活动查询自行结束自己的 loading 生命周期

## 受影响文件

| 文件 | 改动类型 |
|------|---------|
| `app/src/store/entryStore.ts` | 新增查询签名、分页去重 helper、请求回写保护 |
| `app/src/store/__tests__/entryStore.test.ts` | 新增竞态与重复追加测试 |

`Timeline.v2.tsx` 与 `SearchOverlay.tsx` 保持现有交互，不增加临时防抖或 UI 层去重逻辑。

## 测试方案

### 自动化测试

为 `entryStore` 增加以下用例：

1. 同一分页结果返回两次，最终列表不出现重复 `id`
2. 查询 A 发出后切换到查询 B，A 晚返回时不会覆盖 B 的结果
3. 搜索结果首屏后触发分页，若返回页与现有列表存在重复 `id`，最终仅保留一份
4. 同一查询下连续触发两次 `loadMore()`，最终只接受一次有效分页，且 `cursor`、`hasMore`、`isLoadingMore` 状态稳定
5. 过期请求失败时，不会错误地重置当前查询的 loading 状态
6. 数据库表未就绪的延迟重试在签名过期后会被放弃，且不会干扰新查询的 loading 状态

### 手动验证

至少验证以下路径：

1. 打开搜索，输入关键词并提交，关闭 `SearchOverlay` 回到时间线后观察列表，不应立即出现双份
2. 搜索结果页轻微滚动触发加载更多，不应出现同一条记录重复显示
3. 连续切换不同搜索条件，列表应始终与当前条件一致
4. 清空筛选条件后，首页列表恢复正常且不保留旧查询的重复项

## 性能评估

该方案的额外成本可接受：

- 查询签名比较只涉及少量字符串比对
- 去重仅发生在分页 merge 时，不参与每次渲染
- 当前分页大小为 20，按 `entry.id` 合并的成本远低于一次额外重渲染

因此，这次修复以很小的 store 计算开销换取确定性的状态正确性，是合理取舍。

## 不在范围内

- 重写 `SectionList` 的触底策略
- 拆分独立的搜索专用 store
- 修改数据库查询语句或存储结构
- 修复数据库中真实存在的重复写入问题（当前现象不指向此类问题）
