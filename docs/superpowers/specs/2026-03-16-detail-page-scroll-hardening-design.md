# 二级详情页滚动壳加固 — 设计规格

**日期：** 2026-03-16
**状态：** 待实现
**影响文件：**
- `app/src/components/BackupPage.tsx`
- `app/src/components/SettingsPage.tsx`
- `app/src/components/HelpPage.tsx`
- `app/src/components/StatsPage.tsx`
- `app/src/components/Sidebar.tsx`
- `app/src/components/DetailPageShell.tsx`

---

## 1. 需求摘要

当前侧边栏打开的二级详情页都使用同一类结构：

- `Modal`
- 半透明 backdrop
- 右侧滑入的 `Animated.View`
- header
- 内层 `ScrollView`

在 Android 上，`备份与同步` 页面当内容增长到超过可视高度后，页面会显示出超长内容，但无法继续向下滚动。该问题已经在模拟器与真机上复现。由于 `设置 / 帮助 / 统计` 页面沿用同一套页面壳结构，修复应面向整类页面，而不是只给 `BackupPage` 打补丁。

本次目标是统一加固这类二级页的布局和滚动手势分配，保证任一页面内容超出屏幕时都能在 Android 上自然纵向滚动到底部。

---

## 2. 根因判断

从现有实现看，问题更可能来自页面壳结构，而不是备份业务逻辑：

1. 页面主体使用 `height: SCREEN_HEIGHT` 的固定屏高布局，对 Android 实际可视区域和 modal 容器适配较脆弱。
2. header 与 `ScrollView` 外层存在一个 `onStartShouldSetResponder={() => true}` 的包裹层，这会让外层 view 有机会抢占触摸事件，导致纵向滚动手势无法稳定落到 `ScrollView`。
3. 页面底部额外空白通过尾部占位 `View` 撑开，而不是由 `ScrollView` 的 `contentContainerStyle` 统一管理，进一步加大了布局行为不一致的风险。

结论：应优先修正共享页面壳的布局和手势边界，而不是继续针对单个页面追加 `ScrollView` 属性。

---

## 3. 设计方案

### 3.1 抽出共享二级页壳

新增一个共享组件，负责统一处理以下公共结构：

- `Modal` 挂载与卸载
- backdrop 点击关闭
- 右侧滑入 / 滑出动画
- safe area 顶部与底部留白
- header 渲染
- 可滚动内容区

建议组件职责保持很薄，仅封装通用外壳，不承载具体业务数据和业务按钮逻辑。

建议接口形态：

- `visible`
- `onClose`
- `title`
- `children`
- 可选的 `scrollEnabled` 或内容容器样式透传

不在这次设计中引入复杂 slot 系统、手势关闭、标题栏变体等额外能力。

### 3.2 去掉外层 responder 抢占

共享壳中不再保留 `onStartShouldSetResponder={() => true}` 这类会无条件吞掉触摸的包裹层。

新的交互边界应当是：

- backdrop 区域负责点击关闭
- 页面内容区域负责正常点击与滚动
- 纵向拖动优先由 `ScrollView` 接管

这条规则应对所有二级页一致生效。

### 3.3 页面主体改为真实铺满布局

页面主体不再依赖 `Dimensions.get('screen').height` 写死高度，而改成真正随 modal 容器铺满的绝对定位布局。

目标行为：

- 页面壳完整覆盖可视区域
- header 占据顶部固定高度
- 内容区使用剩余空间并允许 `ScrollView` 自然滚动

实现层面可以保留绝对定位的左右与顶部锚点，但高度策略应换成由容器拉伸，而不是屏幕高度常量。

### 3.4 统一滚动容器约定

共享壳中的 `ScrollView` 统一以下约定：

- 内容区横向内边距由容器统一提供
- 底部留白通过 `contentContainerStyle.paddingBottom` 处理
- `showsVerticalScrollIndicator={false}` 继续保持
- Android 需要的滚动兼容配置统一放在共享壳，不分散写在业务页面

这样做之后，业务页面只保留“分区标题 + 卡片内容”，不再直接决定滚动容器怎么撑高。

### 3.5 页面迁移范围

本次应至少迁移以下页面到共享壳：

- `BackupPage`
- `SettingsPage`
- `HelpPage`
- `StatsPage`

`TagsPage`、`AboutPage` 若采用不同结构，可以在实现时判断是否一并纳入；但当前计划只要求覆盖已确认复用同一壳层模式且已读到的四个页面。

`Sidebar` 只更新调用关系，不改菜单行为。

---

## 4. 各页面的保持项

以下行为必须保持不变：

- 侧边栏入口与菜单文案不变
- 点击菜单项后，仍然以当前的右侧滑入方式打开详情页
- 点击 backdrop 关闭
- 点击左上角返回关闭
- 动画方向与时长保持当前体感
- `BackupPage` 的导出、导入、分享、刷新逻辑不变
- `SettingsPage` 的设置读写、通知开关、导出数据、重置设置逻辑不变
- `HelpPage` 的 FAQ 折叠逻辑与邮件跳转不变
- `StatsPage` 的统计计算逻辑不变

换句话说，这次只修“容器壳”，不顺手改业务行为或视觉语言。

---

## 5. 错误处理与边界

### 5.1 内容不足一屏

如果页面内容没有超过可视高度，页面应与当前表现一致：

- 不需要滚动也能完整展示
- header 与底部留白正常
- 点击与关闭交互不受影响

### 5.2 内容超过一屏

如果页面内容超过可视高度：

- 用户应能在内容区任意自然起手纵向拖动
- 可以一路滚动到底部
- 底部最后一块内容不会被系统安全区或额外占位遮住

### 5.3 动画期间与关闭时

打开 / 关闭动画期间不引入新的状态切换逻辑，只维持当前 `shouldRender` / `isAnimating` 行为。

这次不增加：

- 拖拽关闭
- 滚动联动 header 动画
- 根据滚动位置改变 backdrop 或标题样式

### 5.4 平台边界

本次问题在 Android 已确认复现，修复必须以 Android 为验收主目标。

iOS 虽未复现，也不能因为共享壳重构而引入：

- 顶部安全区错位
- 无法点击关闭
- 动画闪动
- 内容裁切

## 6. 测试与验收

### 6.1 手动验证

至少覆盖以下场景：

| 场景 | 预期 |
|------|------|
| Android 打开 `备份与同步`，历史备份较少 | 页面可正常打开、关闭，视觉与当前一致 |
| Android 打开 `备份与同步`，历史备份增多到超过一屏 | 可持续下滑到底部 `iCloud 同步` 区块 |
| Android 打开 `设置 / 帮助 / 统计` | 内容超长或接近满屏时均可正常纵向滚动 |
| 任一二级页点击 backdrop | 正常关闭 |
| 任一二级页点击左上角返回 | 正常关闭 |
| 任一二级页快速开关 | 不出现白屏、内容截断、动画跳变 |

### 6.2 自动化验证

如测试基础允许，可补充轻量组件测试，锁定以下结构性约束：

- 二级页内容区通过共享壳渲染
- 共享壳确实包含滚动容器
- `BackupPage` 在存在备份历史时仍能完整渲染底部区块

不要求在这次为 React Native 手势滚动编写高成本动画测试；这里优先依赖结构收敛与手动回归。

### 6.3 验收标准

验收以一句话定义：

> 任一二级详情页内容超过可视高度时，Android 上都必须可以自然纵向滚动到底部，且关闭、动画与既有业务行为不回退。

---

## 7. 实施边界

本次不包含以下内容：

- 将这些页面改造成 Expo Router 正式路由页
- 重做视觉样式、间距体系、图标或文案
- 统一所有侧边栏页面到完全相同的业务骨架
- 为详情页新增手势返回、吸顶、拖拽交互

本次是一次面向稳定性的页面壳加固，目标是消除 Android 滚动失效，并为后续同类页面提供可复用的安全基线。
