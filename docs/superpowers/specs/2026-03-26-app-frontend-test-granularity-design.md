# App Frontend Test Granularity Design

## 背景

当前项目已经具备较多前端自动化测试，包括：

- React Native 组件测试
- service/store 逻辑测试
- 少量页面级测试
- Android Maestro 云同步流程测试

但现状仍有几个明显问题：

1. 自动化覆盖呈点状分布，模块深度不均匀
2. 高风险前端模块缺少统一的测试拆分标准
3. 页面联动场景经常介于组件测试与 E2E 之间，没有明确归属
4. Android 真流程已经开始建设，但范围仍偏窄
5. 一些测试文件持续膨胀，后续维护成本会越来越高

这次工作的重点不是“再加一些测试”，而是先把 App 前端的自动化测试地图重新拆清楚，明确：

- 哪些模块要优先深挖
- 每一层自动化应该负责什么
- 每条用例应该细到什么粒度
- 当前缺口应该按什么顺序补

## 目标

为 App 前端建立一份 Android 优先的细颗粒度自动化测试设计，满足以下目标：

1. 为核心前端模块提供统一的测试分层标准
2. 将自动化测试按模块、子域和场景拆到可直接转任务的粒度
3. 明确 `Jest-Unit`、`Jest-Page`、`Maestro-Android` 的职责边界
4. 优先覆盖核心业务和高风险设置/同步相关前端场景
5. 为后续补 Jest 与 Maestro 用例提供明确的文件拆分方向

## 非目标

本次不覆盖以下范围：

- iOS 首版完整自动化矩阵
- 后端接口、数据库和 Go 测试设计
- 云同步协议本身的后端设计
- CI 编排、分层并发和执行平台建设
- 全量正式测试用例库导出

这份设计只聚焦 App 前端自动化测试如何更细致、分模块、可持续地演进。

## 平台与范围

本次范围固定为：

- 平台：Android 优先
- iOS：只标注差异点，不做首版完整展开
- 范围：App 前端模块
- 覆盖方式：核心业务 + 高风险设置/同步细拆，其余模块先列二级清单
- 用例粒度：每条用例写到“前置条件 / 操作步骤 / 预期结果 / 异常分支”

## 测试分层

前端自动化固定拆成 3 层，避免职责混乱。

### 1. `Jest-Unit`

覆盖内容：

- 纯逻辑分支
- store 状态迁移
- service 映射规则
- 组件局部交互
- 文案/图标/按钮显示规则
- 错误类型与状态枚举映射

适合验证：

- 某个状态值如何影响 UI
- 某个 service 分支是否触发正确动作
- 某个异常输入是否被安全兜底

不负责：

- 跨页面导航闭环
- Android 返回键
- 前后台切换
- 系统权限弹窗

### 2. `Jest-Page`

覆盖内容：

- 页面初始渲染
- 页面内多个组件之间的联动
- 页面与 store/service 的交互
- 页面级弹窗、状态切换、失败恢复

适合验证：

- 设置页多个分区的联动
- 编辑页中文本、图片、保存、返回保护的联动
- 搜索输入、筛选、结果和退出恢复的联动

不负责：

- 系统级权限弹窗
- 真正的 Android 返回键
- App 后台恢复

### 3. `Maestro-Android`

覆盖内容：

- 页面之间的真实导航链路
- Android 返回键层级
- 系统权限弹窗
- App 前后台切换
- Android 端同步/修复/查看器的真实闭环

适合验证：

- 首页进入详情再返回
- 编辑页未保存退出保护
- 搜索态退出
- 图片查看器返回
- 设置页同步状态入口
- 修复提示与实验入口

不负责：

- 覆盖所有业务分支
- 替代单测和页面测试

### 分层原则

1. 能稳定用 Jest 覆盖的，不上 Maestro
2. 页面联动优先放在 `Jest-Page`
3. Maestro 只保留高价值 Android 真流程
4. 同一个场景不能在 3 层重复堆叠成冗余测试

## 模块优先级矩阵

### P0 核心模块，首批细拆

| 模块 | 覆盖范围 | 风险原因 | 主测层 |
| --- | --- | --- | --- |
| 时间线首页 | Tab 首页、列表渲染、空态、刷新、分组、卡片入口、云同步状态入口 | 访问频率最高，回归直接影响主流程 | `Jest-Unit` + `Jest-Page` + `Maestro-Android` |
| 记录创建/编辑 | 新建记录、编辑已有记录、文本输入、保存、取消、离开页面、草稿状态 | 核心写入路径，状态联动多 | `Jest-Unit` + `Jest-Page` |
| 图片链路 | 选图/拍照、缩略图、九宫格、查看器、缺图、坏图、修复提示 | 资源状态复杂，边界多 | `Jest-Unit` + `Jest-Page` + `Maestro-Android` |
| 搜索与筛选 | 搜索框、搜索浮层、标签筛选、结果态、空结果、清空条件 | 状态组合多，最容易出回归 | `Jest-Unit` + `Jest-Page` + `Maestro-Android` |
| 设置页与云同步入口 | 设置项、云端模式切换、状态查看、修复入口、E2E Lab、后端环境 | 高风险控制面板，和 service/store 耦合最深 | `Jest-Unit` + `Jest-Page` + `Maestro-Android` |

### P1 高风险支撑模块，第二批细拆

| 模块 | 覆盖范围 | 风险原因 | 主测层 |
| --- | --- | --- | --- |
| 登录与账号态 | 登录页、登出、未登录态、登录后状态回流 | 会阻断云能力和部分设置入口 | `Jest-Page` + `Maestro-Android` |
| 备份/恢复 | 备份页、导出、导入、清空本地后的恢复提示 | 数据安全相关，误操作成本高 | `Jest-Page` + `Maestro-Android` |
| 标签管理 | 标签列表、创建、编辑、删除、引用后的表现 | 会影响搜索、筛选、编辑器联动 | `Jest-Unit` + `Jest-Page` |
| 权限与本地环境 | 相册权限、通知权限、存储路径状态、本地环境切换 | Android 差异大，容易出系统级问题 | `Jest-Unit` + `Jest-Page` + `Maestro-Android` |
| 错误反馈与全局兜底 | Error boundary、错误反馈弹窗、全局提示 | 决定异常时能否恢复和回退 | `Jest-Unit` + `Jest-Page` |
| 语音链路 | 录音器、录音状态、上传队列、云模式差异 | 硬件态与后台态复杂 | `Jest-Unit` + `Jest-Page` |

### P2 二级清单，先保留 smoke

| 模块 | 首版策略 |
| --- | --- |
| 关于页 | 页面渲染、关键内容存在、返回链路 |
| 帮助页 | 页面渲染、内容区存在、返回链路 |
| 统计页 | 空数据/有数据两态、返回链路 |
| Sidebar/辅助入口 | 展开、收起、关键跳转 |
| 纯展示型小组件 | 只断言关键结构与关键交互，不堆低价值快照 |

## 模块内颗粒度规则

每个模块内继续拆成 5 层：

1. 入口层：页面进入、初始态、必要数据加载
2. 交互层：点击、输入、切换、滚动、返回
3. 状态层：store 更新、条件渲染、禁用态、已选态
4. 副作用层：调用 service、弹窗、toast、导航、权限请求
5. 恢复层：失败、重试、取消、中断、脏数据、前后台切换

这意味着后续不会写“设置页测试”这种粗项，而是按“模块 -> 子能力 -> 单场景”持续拆分。

## P0 细颗粒度自动化用例

以下为首批必须落地成自动化的 P0 用例清单。每条用例默认写成：

- 前置条件
- 操作步骤
- 预期结果
- 异常分支

### A. 时间线首页

#### `TL-01 首页空态渲染` `Jest-Page`

- 前置条件：本地无记录，未激活搜索和筛选
- 操作步骤：进入首页，等待初始渲染完成
- 预期结果：显示空态内容，主操作入口可见，不渲染记录卡片
- 异常分支：数据加载超时或抛错时，进入错误兜底，不出现空白页

#### `TL-02 有记录时按既定顺序分组渲染` `Jest-Page`

- 前置条件：注入多天、多条记录，覆盖有图和纯文本两类
- 操作步骤：进入首页，读取分组标题和卡片顺序
- 预期结果：分组标题正确，卡片顺序稳定，图片卡与文本卡展示正确
- 异常分支：遇到非法时间字段时，仍可渲染并落入兜底排序

#### `TL-03 卡片点击进入详情页` `Jest-Page` + `Maestro-Android`

- 前置条件：存在至少一条可点击记录
- 操作步骤：点击卡片主体
- 预期结果：进入详情页，详情内容对应，返回后仍回到原列表上下文
- 异常分支：详情加载失败时，应显示错误反馈或降级内容，而不是卡死

#### `TL-04 首页刷新与状态回流` `Jest-Page`

- 前置条件：已有首页数据，store 支持刷新动作
- 操作步骤：触发刷新动作或页面重新聚焦
- 预期结果：刷新状态只在有效窗口内显示一次，完成后列表恢复稳定
- 异常分支：刷新失败时保留旧数据，不允许把已有列表清空成空态

#### `TL-05 云同步状态按钮在首页的显示规则` `Jest-Unit` + `Jest-Page`

- 前置条件：构造未开启、空闲、同步中、异常四种状态
- 操作步骤：渲染首页头部区域
- 预期结果：按钮文案、图标、可点击性与状态一致
- 异常分支：未知状态值时退回安全展示，不抛运行时错误

#### `TL-06 缺图/坏图卡片在时间线中的降级表现` `Jest-Page`

- 前置条件：存在图片路径失效、媒体校验异常、缩略图缺失三类记录
- 操作步骤：进入首页观察异常卡片
- 预期结果：显示占位或修复提示，不撑破布局，不影响其他卡片点击
- 异常分支：多张坏图连续出现时，列表仍可滚动

#### `TL-07 首页滚动过程中的工具栏/FAB 行为` `Jest-Page` + `Maestro-Android`

- 前置条件：准备足够长的记录列表
- 操作步骤：向下滚动、回滚到顶部、快速连续滚动
- 预期结果：FAB、底部工具栏、顶部区域按设计隐藏或恢复
- 异常分支：Android 快速滑动后不应出现闪烁和错位

#### `TL-08 首页前后台切换后的恢复` `Maestro-Android`

- 前置条件：首页已加载记录，应用进入稳定态
- 操作步骤：App 切后台，再切回前台
- 预期结果：恢复到原列表状态，不重复弹无关提示，不丢滚动上下文
- 异常分支：后台期间同步状态变化后，前台恢复应展示最新状态，但不能强制跳页

### B. 记录创建/编辑

#### `ED-01 新建记录默认态` `Jest-Page`

- 前置条件：从首页或主入口进入新建记录
- 操作步骤：打开编辑页，不输入任何内容
- 预期结果：编辑器初始字段、占位文案、保存按钮状态、附件区域状态符合默认配置
- 异常分支：依赖未加载完成时，展示可恢复加载态，而不是错乱可编辑状态

#### `ED-02 编辑已有记录时正确回填` `Jest-Page`

- 前置条件：存在一条包含文本、标签、图片附件的记录
- 操作步骤：进入编辑页
- 预期结果：内容完整回填，附件顺序正确，页面语义为“编辑已有记录”
- 异常分支：某一附件元数据缺失时，文本部分仍可编辑，异常附件单独降级显示

#### `ED-03 文本输入后的脏状态识别` `Jest-Unit` + `Jest-Page`

- 前置条件：进入新建或编辑页
- 操作步骤：输入文本，再删除，再改回原值
- 预期结果：只有真实变更时才标记未保存
- 异常分支：换行、空格、输入法合成等边界下不应误判

#### `ED-04 保存新记录成功链路` `Jest-Page`

- 前置条件：填写满足最小保存条件的内容
- 操作步骤：点击保存
- 预期结果：只触发一次保存动作，处理中状态正确，保存成功后返回正确页面
- 异常分支：连续快速点击保存时不能重复创建记录

#### `ED-05 保存已有记录更新链路` `Jest-Page`

- 前置条件：已有记录被修改
- 操作步骤：点击保存并回到来源页面
- 预期结果：原记录被更新而不是新增，列表/详情显示新内容
- 异常分支：保存成功但回跳失败时，至少保证数据一致

#### `ED-06 离开编辑页时的未保存保护` `Jest-Page` + `Maestro-Android`

- 前置条件：编辑页存在未保存变更
- 操作步骤：点击返回、切 Tab、使用 Android 返回键
- 预期结果：出现确认提示，可继续编辑或放弃修改
- 异常分支：无修改时不应弹确认；不能叠多层提示框

#### `ED-07 保存失败后的保留与重试` `Jest-Page`

- 前置条件：模拟保存接口或本地写入失败
- 操作步骤：点击保存
- 预期结果：输入内容完整保留，错误提示可见，可直接再次保存
- 异常分支：失败后按钮状态必须恢复，不能清空内容

#### `ED-08 草稿恢复与清理` `Jest-Unit` + `Jest-Page`

- 前置条件：存在未提交草稿，覆盖新建草稿和编辑草稿
- 操作步骤：重新进入编辑页，选择恢复或放弃草稿
- 预期结果：恢复时内容准确载入；放弃时草稿被清理
- 异常分支：草稿版本落后于正式记录时，不允许把旧草稿覆盖新记录

#### `ED-09 图片附件与文本共存时的编辑稳定性` `Jest-Page`

- 前置条件：记录包含多张图片并已有文本内容
- 操作步骤：编辑文本、删除一张图、再保存
- 预期结果：文本变更与附件变更同时生效，顺序和引用关系正确
- 异常分支：删除附件失败时，文本修改不应被一起回滚

#### `ED-10 编辑页异常关闭后的恢复` `Maestro-Android`

- 前置条件：进入编辑页并产生未保存内容
- 操作步骤：切后台、系统返回、重新拉起应用
- 预期结果：根据设计恢复到编辑态或草稿恢复态，不丢用户输入
- 异常分支：恢复失败时必须给出清晰提示

### C. 图片链路

#### `IM-01 从编辑页打开图片入口` `Jest-Page`

- 前置条件：进入新建或编辑页面，图片入口可见
- 操作步骤：点击添加图片入口
- 预期结果：打开正确图片来源流程，原有编辑内容不丢失
- 异常分支：连续点击只允许打开一次来源流程

#### `IM-02 从相册选择单张图片后正确回填` `Jest-Page`

- 前置条件：模拟相册返回一张有效图片
- 操作步骤：完成选择并回到编辑页
- 预期结果：附件区出现 1 张缩略图，页面处于已修改状态
- 异常分支：部分元数据缺失时，只要 uri 有效仍可显示

#### `IM-03 多张图片选择后顺序稳定` `Jest-Page`

- 前置条件：模拟一次选择多张图片，返回顺序已知
- 操作步骤：完成多选并回到编辑页
- 预期结果：附件区按选择顺序展示，后续保存和查看器索引一致
- 异常分支：其中一张无效时，只剔除异常项，不能整批失败

#### `IM-04 拍照返回后的插入行为` `Jest-Page` + `Maestro-Android`

- 前置条件：相机权限已授予
- 操作步骤：进入拍照，完成拍摄并确认使用
- 预期结果：回到编辑页后新照片出现在附件区
- 异常分支：取消拍照或返回空结果时，不应新增空附件

#### `IM-05 权限拒绝时的降级提示` `Jest-Unit` + `Maestro-Android`

- 前置条件：相册权限或相机权限被拒绝
- 操作步骤：尝试从对应入口选择图片或拍照
- 预期结果：出现明确权限提示，引导用户去系统设置或使用其他入口
- 异常分支：永久拒绝时不应反复请求系统权限

#### `IM-06 编辑页附件区的缩略图渲染` `Jest-Page`

- 前置条件：记录包含 1 张、3 张、9 张以上图片三种情况
- 操作步骤：分别渲染编辑页附件区
- 预期结果：缩略图尺寸、裁剪、间距、数量提示符合设计
- 异常分支：超长图、超宽图或极小图时布局仍稳定

#### `IM-07 删除单张图片后的状态一致性` `Jest-Page`

- 前置条件：编辑页已有多张图片
- 操作步骤：删除中间一张图片
- 预期结果：对应缩略图立即移除，其余顺序重排，页面保持脏状态
- 异常分支：删除失败时应恢复原列表或给出明确失败提示

#### `IM-08 图片与文本共同编辑时的保存一致性` `Jest-Page`

- 前置条件：编辑页同时修改文本和图片列表
- 操作步骤：新增图片、删除旧图、修改文本后点击保存
- 预期结果：文本和图片变更一次性保存成功
- 异常分支：仅图片处理失败时，应提示局部失败，不静默丢文本

- 前置条件：实验入口可见
- 操作步骤：进入实验页，触发 suspect repairable、repair pending、clear fixtures 等动作
- 预期结果：各按钮调用正确服务，状态回流到设置页或同步状态页
- 异常分支：测试数据准备失败时，应给出明确失败提示

#### `ST-20 后端连接测试入口` `Jest-Page`

- 前置条件：设置页提供服务端地址或连接测试功能
- 操作步骤：执行连接测试
- 预期结果：加载态和成功/失败反馈准确
- 异常分支：超时、DNS 失败、证书异常要区分为用户可理解的提示

#### `ST-21 后端环境切换` `Jest-Page`

- 前置条件：存在多个后端环境或最近服务地址列表
- 操作步骤：切换目标环境并确认
- 预期结果：当前环境更新成功，后续请求使用新环境
- 异常分支：切换失败时必须保留旧环境

#### `ST-22 登出操作对设置页和同步区域的影响` `Jest-Page` + `Maestro-Android`

- 前置条件：用户已登录且处于云端模式或可见账号信息
- 操作步骤：执行登出
- 预期结果：账号态清空，云相关入口按未登录态降级
- 异常分支：登出失败时，不应提前把本地账号 UI 清空

#### `ST-23 设置页中的本地数据清理高风险确认` `Jest-Page`

- 前置条件：设置页提供清空本地数据动作，且本地存在记录
- 操作步骤：点击清理动作并处理确认弹窗
- 预期结果：必须经过确认链路，确认前不执行真实删除
- 异常分支：取消操作后任何数据都不应被触碰

#### `ST-24 设置页前后台切换后的状态刷新` `Maestro-Android`

- 前置条件：设置页已打开，当前显示同步状态或后端环境信息
- 操作步骤：切到后台，再恢复前台
- 预期结果：必要状态重新拉取或安全复用
- 异常分支：后台期间同步状态变化后，前台恢复应在合理时机刷新

#### `ST-25 设置页在弱网/离线时的降级表现` `Jest-Page` + `Maestro-Android`

- 前置条件：网络断开或网络极差
- 操作步骤：进入设置页，尝试查看同步状态、立即同步、测试连接
- 预期结果：离线相关动作明确失败，本地设置项仍可正常切换
- 异常分支：离线状态下不应让整个设置页进入不可操作状态

#### `ST-26 设置页 Android 返回链路` `Maestro-Android`

- 前置条件：设置页内可能存在弹窗、浮层、状态详情或实验页子路由
- 操作步骤：依次触发返回键
- 预期结果：返回键优先关闭最上层弹层，再返回上一级页面
- 异常分支：不能一键直接退出到首页甚至退出 App

## 当前明显缺口

1. 页面级联动覆盖不足  
   组件和 service 测试不少，但时间线、编辑页、搜索页、设置页的整页联动验证仍不足。

2. Android 真机流程覆盖仍偏窄  
   现有 Maestro 已覆盖云同步部分主链路，但仍缺搜索态退出、编辑未保存返回、查看器返回、权限拒绝回退等高频 Android 行为。

3. 图片链路仍是最高风险区  
   目前图片能力包含选图、拍照、缩略图、查看器、缺图坏图、媒体修复和状态回流，单靠现有 service 测试不足以兜住完整前端回归。

4. 搜索与筛选的组合态覆盖不足  
   输入、筛选、详情返回、首页恢复和 Android 返回键这些组合场景最容易出回归。

5. 设置页自动化职责尚未完全拆清  
   现在设置页已经成为前端控制中枢，不应继续用单个超大测试文件承接全部能力。

## 自动化建设比例建议

首版建议按以下比例建设：

- `Jest-Unit / 组件 / service / store`：60%
- `Jest-Page 集成测试`：30%
- `Maestro-Android`：10%

原因：

1. 细颗粒度主要依赖 Jest 承担
2. 页面联动适合 `Jest-Page`
3. Maestro 只保留 Android 端最高价值的真实闭环

## 设计结论

这款 App 当前最需要的不是“更多零散测试”，而是：

1. 按模块边界重新整理前端自动化
2. 把 `Jest` 和 `Maestro` 的职责切开
3. 先补最容易出真实事故的链路
4. 把设置页、图片链路、编辑器和搜索，从“已有一些测试”提升到“有体系的回归保护”

下一步应基于本设计，产出 implementation plan，把首批测试建设拆成可执行任务。
