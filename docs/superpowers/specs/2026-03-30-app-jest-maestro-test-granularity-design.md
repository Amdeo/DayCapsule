# App Jest And Maestro Test Granularity Design

## 背景

当前项目的 `app` 端已经具备较多自动化测试资产，包括：

- React Native 页面和组件测试
- `service/store` 逻辑测试
- Android `Maestro` smoke、app-core、cloud-sync flow

但从当前测试分布看，仍然存在几个结构性问题：

1. 高风险业务域的测试深度不均匀，有些模块覆盖较细，有些仍停留在点状覆盖
2. 页面联动、局部组件分支、状态逻辑和 Android 真流程之间的边界不够统一
3. 现有部分测试文件已经偏大，继续直接堆场景会降低失败定位效率
4. Android `Maestro` 已经起步，但主链路和异常恢复链路还可以继续细化
5. 新增测试如果没有统一地图，后续会继续出现“能跑但不好维护”的问题

这次工作的重点不是泛化为“给项目加更多测试”，而是把 `app` 端的高风险自动化测试重新按业务域和层级拆清楚，让后续实现可以直接按 spec 转成任务。

## 目标

本次设计的目标如下：

1. 为 `app` 端建立一份 Android 优先的高颗粒度测试地图
2. 明确 `Jest-Page`、`Jest-Component`、`service/store`、`Maestro-Android` 各自负责什么
3. 以回归风险为先，优先补强首页主流程、编辑器写入路径、设置与同步异常恢复路径
4. 在提升覆盖率的同时控制测试文件继续膨胀
5. 让后续新增测试时可以按业务域和层级直接落到明确文件边界

## 非目标

本次不覆盖以下范围：

- 后端 Go 测试体系的完整重构
- iOS 首版完整自动化矩阵
- CI 编排、并发分层、云端执行平台建设
- 全量媒体能力矩阵的完整补齐
- 备份、恢复、权限、语音、统计等全部模块的首批细拆
- 为了测试而重构大块生产实现，除非稳定性无法保证

后端只在前端或 Android 真流程存在直接依赖、且缺口明显时考虑少量补位，不作为本轮主轴。

## 范围

本次范围固定为：

- 平台：Android 优先
- 范围：`app` 前端
- 自动化层：
  - `Jest-Page`
  - `Jest-Component`
  - `service/store`
  - `Maestro-Android`
- 产出重点：高风险业务域的细颗粒度场景清单与文件边界
- 执行入口：只做最小整理，不单独开一轮脚本重构

优先级固定如下：

- `P0`
  - 时间线 / 首页 / 搜索
  - 编辑器 / 保存 / 离开保护
  - 设置 / 同步状态 / 修复入口
- `P1`
  - 媒体链路
- 其他模块
  - 先记录候选范围，不在本轮首批展开

## 方案比较

### 方案 A：按现有文件继续加测

做法：

- 在现有 `test.tsx` / `test.ts` 中继续叠加场景
- `Maestro` 直接往现有 flow 目录继续追加

优点：

- 推进快
- 改动面小

缺点：

- 测试文件继续膨胀
- 失败定位会越来越慢
- 页面、组件、逻辑层和真流程的职责仍然混杂

### 方案 B：按业务域重建测试地图

这是推荐方案。

做法：

- 按业务域而不是按文件堆用例
- 每个业务域内部固定拆为页面、组件、逻辑和 Android 真流程
- 执行入口仅做最小整理

优点：

- 最符合“回归优先，同时兼顾可维护性”
- 失败定位清晰
- 后续可以直接按业务域转任务

缺点：

- 比直接堆场景更需要 upfront 设计
- 需要明确去重规则，避免同一语义在多层重复断言

### 方案 C：以 Maestro 真流程为主轴，Jest 做配套

做法：

- 先快速扩大 Android 真流程覆盖
- Jest 只补这些 flow 背后的关键缺口

优点：

- 能最快提高 Android 真回归能力

缺点：

- Jest 侧会偏被动
- 不利于长期形成稳定的前端测试地图

## 最终方案

采用方案 B：按业务域重建测试地图。

原因：

1. 用户明确要求“颗粒度高”
2. 本轮范围聚焦 `app` 端和 Android `Maestro`
3. 目标是回归优先，同时兼顾可维护性

因此，本轮设计采用“业务域优先、层级归位、最小执行入口整理”的结构。

## 分层原则

### 1. `Jest-Page`

负责：

- 页面初始渲染
- 页面内多个区块的联动
- 页面与 store/service 的交互
- 页面级错误反馈、弹窗和恢复语义

适合验证：

- 首页数据态切换
- 搜索与筛选联动
- 编辑器保存与离开保护
- 设置页多个分区的状态联动

不负责：

- Android 系统返回键
- App 前后台切换
- 真权限弹窗
- 真实导航栈闭环

### 2. `Jest-Component`

负责：

- 单个关键组件的状态语义
- 局部分支的结构差异
- 小范围交互和回调语义
- 动画或视觉状态的局部行为

适合验证：

- 同步状态按钮的不同状态结构
- 卡片异常媒体的降级显示
- 编辑器局部禁用态、脏态和按钮状态
- 搜索和筛选控件的局部分支

不负责：

- 整页联动
- 多模块组合闭环
- Android 原生返回和导航层级

### 3. `service/store`

负责：

- store 状态迁移
- service 分支逻辑
- 错误映射与兜底语义
- 页面依赖的关键规则和状态机

适合验证：

- 搜索条件恢复和清理
- 编辑器脏态判定
- 同步状态映射
- 修复入口显示条件
- 保存失败后的恢复规则

不负责：

- 用户可见结构本身
- 页面布局和导航闭环

### 4. `Maestro-Android`

负责：

- 真实页面跳转
- Android 返回键
- 页面栈恢复
- 关键用户路径的真实闭环
- 同步异常恢复链路

适合验证：

- 首页进入搜索和退出
- 首页进入详情并返回
- 编辑器未保存离开保护
- 设置页打开同步状态
- suspect media / repair later / repair confirm
- 图片查看器返回

不负责：

- 穷举所有细小分支
- 替代 Jest 做细颗粒度规则验证
- 覆盖所有视觉细节

## 去重规则

为了避免测试数量增长但有效防线没有同步提升，固定遵守以下规则：

1. 同一语义只在最合适的层验证一次
2. 页面联动优先放在 `Jest-Page`
3. 组件结构和局部高风险状态优先放在 `Jest-Component`
4. 规则和状态机优先放在 `service/store`
5. Android 真流程只保留高价值闭环放到 `Maestro`
6. 已经能稳定在 Jest 覆盖的逻辑，不上 `Maestro`

## 业务域优先级矩阵

### `P0`

| 业务域 | 风险说明 | 主测层 |
| --- | --- | --- |
| 时间线 / 首页 / 搜索 | 最高频入口，主流程回归最敏感 | `Jest-Page` + `Jest-Component` + `service/store` + `Maestro-Android` |
| 编辑器 / 保存 / 离开保护 | 核心写入路径，错误会直接造成数据丢失感 | `Jest-Page` + `Jest-Component` + `service/store` + `Maestro-Android` |
| 设置 / 同步状态 / 修复入口 | 控制面板和异常恢复入口，Android 真流程价值最高 | `Jest-Page` + `Jest-Component` + `service/store` + `Maestro-Android` |

### `P1`

| 业务域 | 风险说明 | 主测层 |
| --- | --- | --- |
| 媒体链路 | 异常组合多，但本轮只补与 `P0` 强耦合部分 | `Jest-Page` + `Jest-Component` + `service/store` + `Maestro-Android` |

### 非首批展开域

保留后续候选，但不在本轮首批展开：

- 登录 / 账号态
- 标签管理
- 统计页
- 备份 / 恢复
- 权限 / 本地环境
- 语音链路
- 全局错误反馈和 fallback 页面

## 统一拆分模板

每个业务域都按相同模板拆场景：

1. 页面进入与初始态
2. 核心交互
3. 状态切换
4. 副作用
5. 错误与恢复
6. Android 真流程

后续实现任务也应按这个模板拆，而不是继续使用“补首页测试”“补设置测试”这类粗粒度描述。

## 场景编号约定

为方便直接转任务和追踪回归，使用固定业务域编号：

- `TL-*`：时间线 / 首页 / 搜索
- `ED-*`：编辑器 / 保存 / 离开保护
- `ST-*`：设置 / 同步状态 / 修复入口
- `MD-*`：媒体链路

## P0 细颗粒度场景

以下场景默认都按以下结构描述：

- 前置条件
- 操作步骤
- 预期结果
- 异常分支

### A. 时间线 / 首页 / 搜索

#### `TL-01 首页空态渲染` `Jest-Page`

- 前置条件：无记录、无搜索、无筛选
- 操作步骤：进入首页并等待初始渲染
- 预期结果：显示空态文案和主入口，不渲染记录列表
- 异常分支：加载失败时显示错误兜底，不进入空白页

#### `TL-02 首页有记录时按既定顺序渲染` `Jest-Page`

- 前置条件：注入多日期、多类型记录
- 操作步骤：进入首页
- 预期结果：分组标题、卡片顺序、文本卡和图片卡基础结构稳定
- 异常分支：异常时间字段走兜底排序，不导致崩溃

#### `TL-03 首页刷新后保留已有内容语义` `Jest-Page`

- 前置条件：已有列表数据
- 操作步骤：触发刷新或页面重新聚焦
- 预期结果：刷新过程不把已有数据闪成空态，完成后列表稳定
- 异常分支：刷新失败时保留旧数据并提供恢复反馈

#### `TL-04 搜索输入后结果联动正确` `Jest-Page`

- 前置条件：准备可命中与不可命中的混合数据
- 操作步骤：进入搜索，输入关键词
- 预期结果：结果列表按关键词收敛，非命中项消失
- 异常分支：空结果显示明确空结果态，不显示旧结果

#### `TL-05 标签筛选与关键词搜索组合生效` `Jest-Page`

- 前置条件：记录带不同标签和文本
- 操作步骤：组合关键词和标签条件
- 预期结果：组合条件共同作用，结果变化符合预期
- 异常分支：清空其中一项条件时，其余条件仍继续生效

#### `TL-06 退出搜索后恢复首页上下文` `Jest-Page`

- 前置条件：首页已有初始列表，已进入搜索态并产生结果
- 操作步骤：关闭搜索浮层或退出搜索态
- 预期结果：回到正常首页列表，非搜索态 UI 恢复
- 异常分支：退出后不残留搜索文案、筛选标记或错误上下文

#### `TL-07 卡片点击进入详情前导航参数正确` `Jest-Page`

- 前置条件：至少存在一条可点击记录
- 操作步骤：点击卡片主体
- 预期结果：触发正确导航并携带对应记录上下文
- 异常分支：记录缺字段时走降级路径，而不是无响应

#### `TL-08 首页同步状态入口显示规则` `Jest-Component` + `Jest-Page`

- 前置条件：构造未开启、空闲、同步中、失败等状态
- 操作步骤：渲染首页头部区域
- 预期结果：入口文案、图标和可点击性与状态一致
- 异常分支：未知状态值安全降级，不抛错

#### `TL-09 异常媒体卡片不会破坏首页列表结构` `Jest-Component` + `Jest-Page`

- 前置条件：构造缺图、坏图、缩略图缺失等记录
- 操作步骤：渲染首页列表
- 预期结果：卡片显示占位或修复提示，其他项仍正常
- 异常分支：连续异常卡片出现时不影响滚动和点击

#### `TL-10 搜索状态逻辑迁移` `service/store`

- 前置条件：构造初始空搜索态
- 操作步骤：依次设置关键词、标签、清空关键词、清空全部
- 预期结果：搜索条件与派生状态准确变化
- 异常分支：空白字符串、非法输入、重复条件不导致状态错乱

#### `TL-11 时间线控制器排序与分组兜底` `service/store`

- 前置条件：输入正常和异常混合记录
- 操作步骤：执行分组和排序逻辑
- 预期结果：输出顺序稳定，异常值进入兜底分组
- 异常分支：单条坏数据不拖垮整个列表

#### `TL-12 首页搜索进入与退出真流程` `Maestro-Android`

- 前置条件：app 已启动到首页
- 操作步骤：打开搜索、输入关键词、取消退出
- 预期结果：搜索 UI 打开成功，退出后回到首页稳定状态
- 异常分支：Android 返回键退出时不残留半打开状态

#### `TL-13 首页进入详情并返回真流程` `Maestro-Android`

- 前置条件：存在稳定 fixture 记录
- 操作步骤：从首页或搜索结果进入详情，再使用系统返回
- 预期结果：回到原列表上下文，不跳错页，不卡在中间层
- 异常分支：详情内容加载异常时也能安全返回

#### `TL-14 首页进入设置并返回真流程` `Maestro-Android`

- 前置条件：首页稳定可见
- 操作步骤：打开侧边栏，进入设置，再返回首页
- 预期结果：首页恢复稳定，可继续交互
- 异常分支：Android 返回层级不出现多退或少退

### B. 编辑器 / 保存 / 离开保护

#### `ED-01 新建记录默认态` `Jest-Page`

- 前置条件：从创建入口进入编辑器
- 操作步骤：页面初始渲染，不输入内容
- 预期结果：基础字段、占位文案、默认按钮状态符合预期，未进入可保存态
- 异常分支：依赖尚未加载完成时展示稳定加载态或安全默认态

#### `ED-02 编辑已有记录时正确回填` `Jest-Page`

- 前置条件：准备已有文本或带附件记录
- 操作步骤：进入编辑页
- 预期结果：文本、标签、附件或相关区域按记录内容回填
- 异常分支：部分字段缺失时仍能进入编辑页，并对缺失字段使用安全默认值

#### `ED-03 仅在形成有效改动后进入可保存态` `Jest-Page` + `service/store`

- 前置条件：进入新建或编辑态
- 操作步骤：输入内容、撤销输入、改回原值
- 预期结果：只有形成有效变化时保存按钮才可用；恢复原值后回到不可保存
- 异常分支：空白字符、无意义重复输入不误判为脏态

#### `ED-04 保存成功后页面状态收敛正确` `Jest-Page`

- 前置条件：输入合法内容
- 操作步骤：点击保存
- 预期结果：触发保存动作，页面进入成功后的稳定状态，必要时返回上一层或关闭编辑态
- 异常分支：短时间重复点击不会触发重复保存

#### `ED-05 保存进行中时避免重复提交` `Jest-Component` + `Jest-Page`

- 前置条件：mock 保存过程为 pending
- 操作步骤：连续点击保存
- 预期结果：按钮进入 loading 或禁用态，只触发一次保存调用
- 异常分支：保存中点击其他高风险操作不会导致状态机错乱

#### `ED-06 保存失败后保留用户输入` `Jest-Page` + `service/store`

- 前置条件：保存动作 reject
- 操作步骤：输入内容并点击保存
- 预期结果：展示失败反馈，但当前输入内容仍保留，用户可以继续修改或重试
- 异常分支：失败后不错误回退到初始空态或旧值

#### `ED-07 离开页面前无改动时不触发拦截` `Jest-Page`

- 前置条件：进入编辑页但未修改
- 操作步骤：点击返回或关闭
- 预期结果：直接离开，不出现未保存确认
- 异常分支：仅聚焦或失焦、未实际修改时不应误报脏态

#### `ED-08 有改动时触发未保存离开确认` `Jest-Page`

- 前置条件：产生有效修改
- 操作步骤：点击返回或关闭
- 预期结果：出现未保存离开确认，保留当前编辑上下文
- 异常分支：多次触发返回时不重复叠加弹窗

#### `ED-09 选择继续编辑时保留原上下文` `Jest-Page`

- 前置条件：已出现未保存离开确认
- 操作步骤：选择继续编辑
- 预期结果：弹窗关闭，内容、按钮状态和编辑上下文保持原样
- 异常分支：不会清空输入，不会误触发保存

#### `ED-10 确认离开时正确丢弃未保存内容` `Jest-Page`

- 前置条件：已出现未保存离开确认
- 操作步骤：选择放弃修改并离开
- 预期结果：退出编辑页，未保存内容不进入正式数据
- 异常分支：返回上一页后不残留编辑中的脏状态

#### `ED-11 编辑器脏态判定规则` `service/store`

- 前置条件：准备初始记录和值
- 操作步骤：依次测试新增、删除、恢复原值、空白字符变动等情况
- 预期结果：脏态判断符合业务语义，而不是简单字符串不等
- 异常分支：字段顺序变化、标准化前后差异不造成假脏态

#### `ED-12 保存状态机迁移` `service/store`

- 前置条件：构造 idle、dirty、saving、failed、saved 等状态
- 操作步骤：触发保存成功、失败、重试、取消
- 预期结果：状态迁移明确，失败后允许恢复，成功后收敛
- 异常分支：非法迁移不会让状态卡死在 saving

#### `ED-13 编辑器局部禁用与反馈语义` `Jest-Component`

- 前置条件：分别构造不可保存、正在保存、失败反馈和可重试场景
- 操作步骤：渲染局部控件
- 预期结果：按钮、提示、输入区禁用态与反馈语义正确
- 异常分支：未知状态值安全降级，不抛错

#### `ED-14 Android 返回触发未保存离开保护` `Maestro-Android`

- 前置条件：通过稳定入口进入编辑器并制造未保存修改
- 操作步骤：按系统返回键
- 预期结果：出现未保存确认，而不是直接返回
- 异常分支：快速连续按返回时不出现双弹窗或漏拦截

#### `ED-15 取消离开后继续编辑真流程` `Maestro-Android`

- 前置条件：已触发未保存离开确认
- 操作步骤：选择继续编辑
- 预期结果：回到编辑器并保留刚才输入内容
- 异常分支：页面不重置、不跳转、不丢上下文

#### `ED-16 确认离开后回到原页面真流程` `Maestro-Android`

- 前置条件：已触发未保存离开确认
- 操作步骤：确认放弃修改
- 预期结果：回到来源页面，返回栈正常，可继续后续操作
- 异常分支：不会卡在半透明弹窗层或错误页面

## 执行入口最小整理

本轮不单独重构脚本体系，但增加测试时应遵守以下原则：

1. 新增 `npm` 脚本优先按业务域组织，而不是无限按单文件堆命令
2. `Maestro` 继续保留少量高价值分组，不新建大量平行目录
3. 一个命令只服务一类回归目标，避免把主链路、异常媒体和复杂前置场景强行混跑

建议的最小执行分组如下：

### Jest

- `timeline/home/search`
- `editor/save/leave-guard`
- `settings/sync/repair`
- `media-linked-regressions`

### Maestro

- `app-core`
  - 首页搜索进入退出
  - 首页详情返回
  - 首页设置返回
  - 编辑器未保存离开保护
  - 图片查看器返回
- `cloud-sync`
  - 设置页打开同步状态
  - suspect media
  - repair later
  - repair confirm
  - 修复入口再次拉起

## 实现顺序建议

后续实现建议固定按以下顺序推进：

1. `TL` 时间线 / 首页 / 搜索
2. `ED` 编辑器 / 保存 / 离开保护
3. `ST` 设置 / 同步状态 / 修复入口
4. `MD` 媒体链路补位
5. 最后补少量执行入口整理

这样可以保证先建立主流程防线，再补数据写入，再补控制面板和异常恢复，最后处理媒体扩展与执行入口清理。

## 验证标准

当这份 spec 后续转为 implementation plan 并开始落地时，完成标准应至少满足：

1. `P0` 三个业务域都有明确新增测试，不只停留在文档中
2. `Maestro` 新增 flow 覆盖首页主链路和同步异常恢复链路
3. 页面、组件、逻辑和真流程的职责边界清晰，没有明显重复断言
4. 至少补出一组按业务域组织的最小执行入口
5. 新增测试不显著恶化现有测试文件可维护性

## 总结

本次设计的核心不是“把测试数量做多”，而是建立一张围绕高风险业务域展开的测试地图：

- 用 `Jest-Page` 锁页面联动
- 用 `Jest-Component` 锁局部高风险结构
- 用 `service/store` 锁规则和状态机
- 用 `Maestro-Android` 锁真实 Android 闭环

在此基础上，优先保护首页主流程、编辑器写入路径、设置与同步异常恢复，再以媒体链路做第二批补位。
