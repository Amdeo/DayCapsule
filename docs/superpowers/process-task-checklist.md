# 任务执行流程检查清单

## 适用范围

适用于所有需要经过 `brainstorming -> spec -> plan -> 实现 -> 验证` 链路的任务。

目标不是约束写法，而是确保每个任务都可追踪、可审计、可回看。

---

## 标准链路

1. `brainstorming`
2. 设计确认
3. spec 落盘
4. spec review loop
5. 用户 review gate
6. plan 落盘
7. 按 plan 执行
8. 验证
9. 文档收口

任一步缺失，都不算严格完成。

---

## 每一步必须留下的证据

### 1. Brainstorming

- 有明确的问题定义、范围、约束、成功标准
- 如果涉及交互或结构调整，有明确设计结论
- 不允许在设计未确认前直接进入实现

### 2. 设计确认

- 设计结论需要被用户明确确认
- 确认后才能写 spec

### 3. Spec 落盘

- 路径：`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
- 文档至少包含：
  - 背景
  - 目标
  - 最终方案
  - 影响范围
  - 不在范围内
  - 验收标准
- 状态字段必须明确，推荐值：
  - `待评审`
  - `已批准`
  - `已实现`

### 4. Spec Review Loop

- 不能只在对话里“口头 review”
- 必须有可追踪证据，二选一即可：
  - 在 spec 中增加“评审记录”
  - 单独存放 review note
- 如果 review 提出了修改，spec 需要同步更新

### 5. 用户 Review Gate

- 用户确认 spec 后，才能进入 plan
- 这个确认必须可追踪
- 最低要求：在 spec 中记录确认日期，或在提交说明中明确引用

### 6. Plan 落盘

- 路径：`docs/superpowers/plans/YYYY-MM-DD-<topic>.md`
- 必须引用对应 spec
- 必须拆成可执行 task
- 每个 task 要有明确文件范围和验证方式

### 7. 按 Plan 执行

- plan 不是一次性产物，必须作为执行清单使用
- 至少 task 级别要同步更新状态
- 如果实现偏离 plan，必须补充说明原因和调整点

### 8. 验证

- 至少记录本次任务实际运行过的验证项
- 常见项包括：
  - `npx tsc --noEmit`
  - 目标测试
  - 全量测试
  - 必要的手动验证
- 不能只说“应该没问题”，必须有实际结果

### 9. 文档收口

- 实现完成后，至少同步以下内容：
  - spec 状态更新为 `已实现` 或等价状态
  - plan 中已完成 task/验收项更新
  - 最终验证结果补齐
- 如果实际实现和原设计有偏差，要在 spec 或 plan 中补充最终说明

---

## 红线

- 没有设计确认，不进入实现
- 没有 spec，不进入 plan
- 没有用户确认 spec，不进入 plan
- 没有 plan，不开始正式实现
- 没有验证结果，不宣称完成
- 代码完成但文档状态未收口，视为流程未完成

---

## 完成前核对清单

- [ ] 已完成 brainstorming，并形成明确设计结论
- [ ] 用户已确认设计
- [ ] spec 已落盘，状态正确
- [ ] spec review 有留痕
- [ ] 用户 review gate 有留痕
- [ ] plan 已落盘并引用 spec
- [ ] plan 已作为执行清单更新
- [ ] 已运行必要验证命令并记录结果
- [ ] spec / plan 状态已收口
- [ ] 最终结论与实际实现一致

---

## 建议

每个任务收尾时，优先检查文档是否闭环，而不是只检查代码是否已经能跑。
